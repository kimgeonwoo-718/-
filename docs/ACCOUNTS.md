# 계정과 구독 공유 (설계)

안드로이드·아이폰·윈도우가 **구독 하나를 같이 쓰게** 하려고 만든다.
이 문서는 세 세션이 다 읽는다 — 서버는 안드로이드 세션이, 윈도우 쪽 소비는 윈도우 세션이 맡는다.

## 왜 필요한가

구독은 지금 **구글 플레이 구매 토큰** 하나로 돌아간다. 폰을 바꿔도 같은 구글 계정이면
Play 가 복원해 주니 안드로이드 안에서는 문제가 없다.

문제는 밖이다.

| | 스토어 | 구매 토큰을 얻을 길 |
|---|---|---|
| 안드로이드 | Google Play | 있다 |
| 아이폰 | App Store | **다른 스토어다.** Play 구매를 모른다 |
| 윈도우 | **없다** | 아예 없다 |

윈도우에는 스토어가 없어서 "이 사람이 구독자인가" 를 물어볼 데가 없다. 그래서 계정이 필요하다.

## 구조 — 계정은 구매를 가리키는 포인터다

**구독 상태의 진실은 여전히 Play 다.** 계정은 "누가 어떤 구매를 샀나" 만 기억한다.

    계정 ──가리킴──> 구매 토큰 ──확인──> Google Play (또는 App Store)

이렇게 두는 이유:

- **환불·해지·만료를 우리가 따로 관리하지 않는다.** Play 가 아니라고 하면 아니다.
- 하루 한도는 지금처럼 **구매 토큰 해시**로 센다. "결제 하나에 한도 하나" 가 그대로 산다.
- 계정 표가 날아가도 안드로이드는 멀쩡하다 — 거긴 Play 에 직접 묻는다.

### 흐름

**안드로이드 (구매하는 곳)**

1. Play 로 결제 → 앱이 구매 토큰을 받는다 (지금 그대로)
2. 사용자가 설정에서 로그인
3. 앱이 서버에 `{신원 증명, 구매 토큰}` 을 보낸다 → 서버가 계정에 구매를 붙인다

**윈도우·아이폰 (쓰기만 하는 곳)**

1. 사용자가 로그인
2. 서버가 그 계정에 붙은 구매 토큰을 찾아 Play 에 확인
3. 구독 중이면 AI 기능이 열린다

## 신원 증명을 무엇으로 할 것인가 — 갈림길

나머지는 다 같고 **이것 하나만 갈린다.**

### (가) 소셜 로그인 (구글 / 애플)

앱이 구글 로그인으로 ID 토큰을 받아 서버에 준다. 서버가 구글 공개키로 서명을 확인하고
`sub`(계정 고유 번호)를 해시해서 계정 열쇠로 쓴다. **이메일은 저장하지 않는다.**

- 좋은 점: 기기를 다 잃어도 로그인만 하면 돌아온다. 사람들이 아는 방식이다.
- 나쁜 점:
  - **윈도우가 번거롭다.** 데스크톱에는 구글 SDK 가 없어서 OAuth 기기 코드 흐름이나
    브라우저를 띄워 되돌려받는 길을 직접 짜야 한다.
  - **Play 정책 의무가 생긴다.** 계정을 만드는 앱은 앱 안 계정 삭제 + 웹에서 삭제를
    요청할 주소를 둬야 한다.
  - 아이폰에 구글 로그인을 넣으면 **애플 로그인도 같이 넣어야 한다**(App Store 심사 규정).
  - 키보드 앱이 계정을 모은다는 것 자체가 신뢰 비용이다.

### (나) 연결 코드 (이메일 없음)

안드로이드 앱이 여섯 자리 코드를 띄운다. 윈도우·아이폰에서 그 코드를 입력하면 서버가
두 기기를 같은 구매에 묶는다.

- 좋은 점:
  - **개인정보를 하나도 안 모은다.** Play 계정 삭제 의무도 안 생긴다.
  - 윈도우 쪽이 "숫자 여섯 개 입력" 으로 끝난다. 애플 로그인 규정도 안 걸린다.
  - 키보드 앱의 "우리는 아무것도 안 가져갑니다" 와 결이 맞는다.
- 나쁜 점:
  - **안드로이드를 아주 버리면 복구가 막힌다.** 코드를 새로 뽑을 데가 없어진다.
    (같은 구글 계정으로 안드로이드에 다시 깔면 Play 가 복원해 주므로, 폰을 잃는 것
    자체는 괜찮다. 안드로이드를 영영 안 쓰게 되는 경우만 막힌다.)

## 권하는 것

**둘 다 만들되 (나)부터.** 코드가 거의 겹친다 — 계정 표와 "구매 토큰 찾아 Play 에 확인"
경로는 공통이고, 갈리는 것은 **신원을 무엇으로 확인하느냐** 한 겹뿐이다.

(나)로 윈도우를 먼저 열고, 아이폰을 낼 때 (가)를 얹는 것이 순서다. 그때는 애플 로그인이
어차피 필요하고, Play 계정 삭제 의무도 그때 같이 처리하면 된다.

## 서버가 가질 것

    CREATE TABLE accounts (
      id             TEXT PRIMARY KEY,   -- 무작위
      purchase_token TEXT,               -- 이 계정이 가진 구매
      store          TEXT,               -- 'play' | 'appstore'
      created_at     INTEGER NOT NULL,
      updated_at     INTEGER NOT NULL
    );

엔드포인트 둘.

| | 누가 | 하는 일 |
|---|---|---|
| `POST /v1/account/link` | 구매한 기기 (안드로이드) | 구매를 계정에 붙인다 |
| `POST /v1/account/subscription` | 쓰기만 하는 기기 (윈도우·아이폰) | 계정 → 구매 → Play 확인 → 구독 상태 |

**구매 토큰을 D1 에 저장하게 된다.** 지금은 안 하던 일이다. 토큰은 그 자체가 구독
증명이라, 새면 남이 쓴다. 저장은 하되 **밖으로 다시 내보내지 않는다** — 확인 결과
(구독 중이냐 아니냐)만 돌려준다.

## 아직 안 정한 것

- 윈도우가 AI 를 부를 때 무엇을 헤더에 실을 것인가. 지금 안드로이드는 구매 토큰을 그대로
  싣는데, 윈도우에 구매 토큰을 내려보내면 그게 새는 통로가 된다. **짧게 사는 세션 토큰**을
  따로 내주는 편이 맞다.
- 한 계정에 기기를 몇 대까지 붙일 것인가. 하루 한도가 구매 하나에 하나라 나눠 쓰게 되지만,
  무제한으로 열어 두면 코드를 퍼뜨릴 수 있다.
