# 맞춤법 키보드 (실시간 교정 IME)

타이핑을 따라가며 한국어 맞춤법과 띄어쓰기를 고치는 안드로이드 키보드.

## 왜 IME 인가

다른 앱에 입력하는 글자를 실시간으로 고치려면 키 입력을 직접 받아야 한다.
안드로이드에서 그게 가능한 건 `InputMethodService` 뿐이다.

- **접근성 서비스**: 다른 앱의 텍스트를 읽고 쓸 수는 있지만, Google Play 가
  접근성 API 오남용을 강하게 규제해서 심사에서 막힐 가능성이 크다.
- **`ACTION_PROCESS_TEXT`**: 안전하고 쉽지만 사용자가 텍스트를 선택해야 한다.
  실시간이 아니다.
- **클립보드 감시**: Android 10 부터 백그라운드 읽기가 막혔다.

## 모듈 구조

```
core/       순수 Kotlin/JVM. 안드로이드 의존성 없음.
            HangulAutomata  - 두벌식 오토마타
            CorrectionEngine - 규칙 기반 교정 엔진
keyboard/   안드로이드 IME. core 를 가져다 쓴다.
            SpellKeyboardService - InputMethodService
            KeyboardView         - 소프트 키보드 화면
            SetupActivity        - 키보드 활성화/시험 화면
```

교정 엔진을 안드로이드에서 떼어 놓은 이유는 두 가지다. 첫째, JVM 단위 테스트로
전부 검증할 수 있다(에뮬레이터 불필요). 둘째, Windows 버전을 만들 때 이 모듈을
그대로 재사용한다.

## 교정이 일어나는 시점

**글자마다 고치지 않는다.** 한글은 조합 중인 음절이 계속 바뀌기 때문에
(`ㅇ → 아 → 안 → 안ㄴ → 안녀 → 안녕`) 조합이 끝나기 전에 손대면 입력이 깨진다.

그래서 **어절이 확정되는 순간** — 스페이스, 문장부호(`. , ! ? ; :`), 엔터 —
커서 앞 최대 3어절을 검사한다. 체감은 실시간이고, 조합 상태와 충돌하지 않는다.

```
사용자 입력:  할수있다[스페이스]
1. 조합 중인 '다' 확정
2. 커서 앞 "할수있다" 를 교정 -> "할 수 있다"
3. deleteSurroundingText(4) + commitText("할 수 있다")
4. 스페이스 입력
```

3번의 지우고-다시-쓰기는 `beginBatchEdit()` 으로 묶는다. 묶지 않으면 편집기가
중간 상태를 그려서 글자가 깜빡인다.

## 되돌리기

교정 직후 백스페이스를 한 번 누르면 원래 입력으로 되돌린다. 자동 교정에서 이게
없으면 고유명사나 신조어를 아예 쓸 수 없게 된다.

되돌리기 전에 편집기의 실제 내용이 우리가 쓴 그대로인지 확인한다. 그사이 커서가
움직였거나 다른 주체가 텍스트를 바꿨을 수 있기 때문이다.

## 교정 엔진의 설계 원칙

**오교정 한 번이 미교정 열 번보다 나쁘다.** 신조어나 고유명사를 멋대로 고치면
사용자는 앱을 지운다. 그래서 규칙에 들어가는 기준은 하나다 —
*문맥 없이도 거의 항상 틀린 표기만 넣는다.*

의도적으로 뺀 것들:

| 항목 | 뺀 이유 |
|---|---|
| 로서 / 로써 | 자격인지 수단인지 의미를 알아야 갈린다 |
| 던지 / 든지 | 회상인지 선택인지 문맥이 필요하다 |
| 반드시 / 반듯이 | 동음이의 |
| 의존명사 '뿐' | '말뿐이다'(조사, 붙임) 와 '할 뿐이다'(의존명사, 띄움) 가 같은 형태 |
| 의존명사 '리' | 받침 ㄹ + 리 는 '달리다·걸리다·알리다' 같은 동사와 충돌 |
| 낳다 / 낫다 | "빨리 낳으세요" 는 오타지만 "아기 낳으세요" 는 정상 |

의존명사 띄어쓰기는 **앞뒤를 둘 다** 확인한 뒤에만 띄운다. 예를 들어 '수'는
앞에 관형형 어미(받침 ㄹ)가 있고 뒤에 '있/없'이 올 때만 띄운다. 이렇게 해야
'실수 있다' 같은 오교정이 안 나온다. 여기에 더해 '별수·실수·홀수·술수' 같은
명사는 예외 목록으로 막는다.

## 이 규칙 엔진이 못 하는 일

**일반적인 띄어쓰기 복원은 못 한다.** "제가할게요" 처럼 통째로 붙여 쓴 문장을
나누려면 형태소 분석기나 문자 단위 딥러닝 모델이 필요하다. 규칙만으로 그걸
하려 들면 오교정이 폭발한다.

다음 단계는 문자 단위 띄어쓰기 모델(TFLite)을 3계층으로 얹는 것이다.
1계층(규칙 사전)과 2계층(조사·어미 규칙)은 1ms 미만, 3계층 모델은 5~15ms 예산이면
타이핑 간격(100~200ms) 안에 들어간다.

**LLM 은 실시간 경로에 못 쓴다.** API 왕복이 200~1000ms라 타이핑을 따라갈 수 없다.
쓴다면 사용자가 명시적으로 누르는 "문장 전체 정밀 교정" 버튼 뒤에 놓아야 한다.

## 개인정보

입력한 글자가 전부 지나가는 앱이다.

- 교정은 전부 온디바이스에서 끝난다. 네트워크 권한을 선언하지 않는다.
- 비밀번호·이메일·URL 입력란(`TYPE_TEXT_VARIATION_PASSWORD` 등)에서는 교정을 끈다.
- `TYPE_TEXT_FLAG_NO_SUGGESTIONS` 를 준 입력란도 존중한다.
- 입력 내용을 저장하거나 학습에 쓰지 않는다.

Play 스토어에 올릴 때 키보드 앱은 이 부분을 심사에서 본다. 서버 전송을 추가하는
순간 개인정보 처리방침과 고지가 필수가 된다.

## 빌드와 테스트

```bash
# 교정 엔진 단위 테스트 (안드로이드 SDK 불필요)
./gradlew :core:test

# 키보드 APK
./gradlew :keyboard:assembleDebug
```

`:core:test` 는 41개 테스트로 오토마타와 교정 엔진을 검증한다. 절반이
**오교정 방지 테스트**다 — 고치면 안 되는 문장이 그대로 남는지 확인한다.

## 설치 후

APK 를 깔았다고 바로 쓸 수 있는 게 아니다. 앱을 열어

1. 시스템 설정에서 키보드 활성화
2. 입력기로 선택

두 단계를 거쳐야 한다. `SetupActivity` 가 두 화면을 바로 열어 주고, 시험용
입력란도 함께 둔다.

## 남은 일

- 문자 단위 띄어쓰기 모델(TFLite) 3계층으로 추가
- 규칙 사전 확장 (현재 약 120항목)
- 교정 이력 화면 — 무엇을 얼마나 고쳤는지
- 사용자 사전 (고유명사·신조어 제외 목록)
- Windows 버전: `core` 를 그대로 쓰고 TSF 또는 키보드 훅으로 붙인다
