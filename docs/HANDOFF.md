# 이어서 작업하는 사람에게

맞춤법 키보드(`core/`, `keyboard/`) 작업 인계 메모. 세션이 끊겨도 여기부터 읽으면 된다.

브랜치: `claude/auto-spell-spacing-checker-r4ymq5`
APK: https://github.com/kimgeonwoo-718/-/releases/tag/apk-latest (푸시할 때마다 갱신)

---

## 지금 어디까지 왔나

목표는 **타이핑을 따라가며 실시간으로 맞춤법·띄어쓰기를 고치는 안드로이드 키보드(IME)**.
카카오톡 수준의 즉각적인 교정이 기준선이다.

동작이 **검증된** 것 (JVM 테스트 88개, `./gradlew :core:test`):

| 부품 | 상태 |
|---|---|
| 한글 두벌식 오토마타 | 겹받침·복합모음·받침이동·백스페이스 역조합까지 |
| 규칙 교정 | 맞춤법 ~120항목 + 띄어쓰기 패턴 |
| 띄어쓰기 (`Spacer`) | mecab-ko-dic + 연결비용 행렬 Viterbi. `아버지가방에들어가신다` 갈림. 어절당 0.25ms |
| 맞춤법 (`Speller`) | 분석비용 비교. `안녕하새요`, `햇는대요` 잡음 |
| Gemini 교정 | 요청 조립·응답 파싱·오류 처리·모델 자동 교체 |

**즉 엔진은 다 됐다.** 남은 건 전부 안드로이드 연결부와 실기기 동작이다.

---

## 아직 안 되는 것 (여기서부터 시작)

사용자가 마지막으로 확인한 결과: **실기기에서 여전히 만족스럽게 동작하지 않음.**
어느 부분이 어떻게 안 되는지는 아직 못 들었다. 그걸 먼저 물어야 한다.

직전 커밋(`7b51c21`)에서 고친 것 — 아직 사용자 확인 전:

1. **`Speller` 가 키보드에 연결조차 안 돼 있었다.** `loadSpacingDictionary()` 에서
   `Spacer` 만 넣고 `session.engine.speller` 는 null 로 뒀다. 즉 지금까지 실기기에서는
   규칙 목록에 없는 오타가 **하나도** 안 잡혔다. 사용자가 계속 말한
   "교정 안 되는 게 너무 많다" 의 유력한 원인. → 연결함.
2. **AI 버튼이 "교정하는 중…" 에서 안 움직임.** 모델 자동 교체 경로가 붙으면서
   요청이 최대 3회 오가는데 건당 타임아웃이 40초였다. → 20초 워치독 + 건당 13초로 축소.

## 이 환경의 제약 (매번 걸려 넘어지는 것들)

- **AGP 를 못 받는다.** `dl.google.com` 이 프록시에서 403. `:keyboard` 모듈은
  **이 컨테이너에서 컴파일조차 안 된다.** 안드로이드 코드 검증은 CI 가 유일한 경로다.
- `:core` 만 로컬에서 돈다. 그것도 별도 `settings.gradle.kts` 를 스크래치패드에 만들어
  `./gradlew -p <scratch> :core:test` 로 돌려야 한다 (루트 빌드는 AGP 때문에 죽는다).
- **실기기 로그를 볼 수 없다.** logcat 없음. 그래서 지금까지 계속 추측으로 고쳐 왔고,
  그게 이 프로젝트가 느리게 진행된 가장 큰 이유다.
- Actions 아티팩트(Azure 블롭)도 막혀 있다. APK 전달은 릴리스 경유만 가능.
- 위키 덤프·HuggingFace 차단. 한국어 코퍼스를 못 구해서 딥러닝 모델 학습은 불가.
  PyPI 는 열려 있다 (mecab-ko-dic 을 여기서 구했다).

## 다음에 할 일

**먼저 사용자에게 이것부터 물어라. 추측으로 고치지 마라.**

1. 어떤 문장이 안 고쳐졌나 (정확한 글자)
2. 키보드 **상단 줄에 뜬 문구** — 진단 정보가 전부 거기 나온다:
   - `검사함: … · 고칠 것 없음` → 엔진까지 갔는데 규칙/사전이 안 걸림
   - `커서 앞 글자를 읽지 못했습니다` → `getTextBeforeCursor` 실패 (mirror 폴백 확인)
   - `이 입력란에서는 교정하지 않습니다` → `isCorrectableField` 판정 문제
   - 아무 변화 없음 → 키 입력 자체가 안 들어옴
3. 설정 화면 **"교정 엔진 점검하기"** 결과 — 여기가 전부 OK 인데 키보드에서 안 되면
   원인은 100% 연결부다. `띄어쓰기 사전: 준비됨` 이 뜨는지도 같이 본다.
4. AI 가 안 되면 **"이 키로 쓸 수 있는 모델 보기"** 버튼 결과

### AI 교정이 계속 실패한다면

`GeminiCorrector.DEFAULT_MODEL = "gemini-3.5-flash-lite"` — 구글이 2.x 를 404 로 거절하며
직접 지목한 이름이다(2026-09). 서버가 거절하면 `ListModels` 로 자동 교체한다. 진단 화면의
실패 줄에는 번역문 아래 "원문:" 으로 예외 종류와 서버 메시지 앞부분이 같이 찍힌다.
"Deploy AI server" 로그 끝에는 CI 가 서버를 거쳐 모델 목록과 교정 한 번을 보낸 결과가 있다.

### 품질을 더 올리려면

지금 `Speller` 는 자모 혼동집합 기반 2회 편집까지만 본다. 문맥이 필요한 판단
(로서/로써, 든지/던지)은 원리적으로 못 한다. 그건 AI 버튼의 영역이거나,
문자 단위 딥러닝 모델이 필요하다 (코퍼스가 없어서 이 환경에서는 불가).

## 설치할 때 주의

CI 가 매번 **다른 디버그 키로 서명**한다. 덮어쓰기 설치가 "서명이 일치하지 않습니다"
로 실패하므로, 새 APK 를 깔 때는 **기존 앱을 먼저 지워야 한다.** 매번 안내할 것.

Play Protect 경고는 정상이다 — 사이드로드 + 디버그 서명 + 키보드 앱 조합이라
구조적으로 악성 키보드와 똑같이 생겼다. 앱은 `INTERNET` 권한만 쓰고, 그것도
AI 교정에만 쓴다 (온디바이스 교정은 네트워크 없이 동작).

## 설계에서 흔들리지 말 것

- **오교정 한 번이 미교정 열 번보다 나쁘다.** 문맥 없이도 거의 항상 틀린 표기만 고친다.
  신조어·고유명사·은어는 건드리지 않는다.
- **실시간 경로에 네트워크를 쓰지 않는다.** 타이핑 간격이 100~200ms 인데 API 왕복은
  수백 ms 다. AI 는 사용자가 버튼을 눌렀을 때만.
- **로직은 안드로이드 밖에 둔다.** `TypingSession` + `FakeEditor` 로 "스페이스를 눌렀을 때
  화면이 어떻게 바뀌는가" 를 JVM 테스트로 재현할 수 있다. 실기기 로그가 없는 환경에서
  이게 유일한 방어선이다.

## AI 중계 서버 + Play 구독 (2026-09-11)

앱에는 Gemini 키가 **없다.** 사용자가 자기 키를 넣지 않으면 `server/`(Cloudflare Worker)로
보내고, 서버가 키를 붙여 구글로 넘긴다. 서버가 무료 한도(설치 ID 당 하루 5 회)를 세고,
`X-Purchase-Token` 을 Play Developer API 에 물어 구독자를 가린다. 폰의 요금제 스위치는
없앴다 — 폰에 저장된 값은 누구나 고칠 수 있다.

```
앱 ──(X-Install-Id, X-Purchase-Token)──▶ Worker ──(x-goog-api-key)──▶ Gemini
                                          ├─ D1: 설치 ID·IP 별 하루 사용량
                                          └─ Play API 로 구독 확인 (1시간 캐시)
```

서버 로직은 `server/test` 에 있고 `node --test` 로 돈다(의존성 없음). 앱은 호스트만
바꾸므로 모델 고르기·갈아타기 로직과 그 테스트는 그대로다.

### 사용자가 해야 하는 것 (순서대로)

**1. Cloudflare** — https://dash.cloudflare.com 가입(무료)
- 오른쪽 위 프로필 → My Profile → API Tokens → Create Token → "Edit Cloudflare Workers" 템플릿
  → Continue → Create Token → 복사
- Workers & Pages 페이지 오른쪽에 Account ID 가 보인다 → 복사
- GitHub 비밀값: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`
- GitHub 비밀값 `GEMINI_API_KEY` 에 AI Studio 키. 이게 없으면 서버는 뜨지만 교정 요청마다
  503(`server_not_configured`)을 돌려준다.
- `server/**` 를 건드린 푸시(또는 Actions 에서 "Deploy AI server" 수동 실행)가 D1 을 만들고
  workers.dev 이름을 API 로 정하고(계정당 한 번, 대시보드 안 거침) 배포한다. 실행 요약 위에
  노란 notice 로 주소가 뜬다: `https://spell-keyboard.<이름>.workers.dev`
- Cloudflare 토큰은 "Edit Cloudflare Workers" 템플릿에 **Account / D1 / Edit** 를 더해야 한다.
  Account ID 는 대시보드 주소창의 32 자리다 (새 대시보드에는 따로 적힌 칸이 없다).
- 그 주소는 build-apk.yml 에 기본값으로 박혀 있다(비밀 아님). 서버를 옮기면 GitHub 변수
  `AI_SERVER_URL` 로 덮어쓴다. 진단 화면 첫 줄이 "중계 서버 경유" 로 나오면 앱이 서버를 쓰는 것.

**2. Play Console** — https://play.google.com/console 개발자 등록($25, 개인 가능)
- 앱 만들기 → 패키지 `com.spellkeyboard.ko`
- 수익 창출 → 구독 → 구독 만들기: 상품 ID **`ai_unlimited_monthly`** (BillingManager 와
  글자 하나까지 같아야 한다), 기본 요금제 월 2,990 원
- 내부 테스트 트랙에 APK 올리고 테스터 이메일 등록 → 그 링크로 설치한 앱에서만 결제창이 뜬다.
  사이드로드한 APK 에서는 Play 결제가 "상품을 찾지 못했습니다" 로 끝난다 — 정상이다.
- 설정 → API 액세스 → 서비스 계정 만들기(Cloud Console 로 넘어감) → 키(JSON) 만들기 →
  Play Console 로 돌아와 그 계정에 "재무 데이터 보기" 권한 부여
- 그 JSON 파일 내용을 통째로 GitHub 비밀값 `PLAY_SERVICE_ACCOUNT` 에 → 서버 재배포
  ("Deploy AI server" 수동 실행). 이게 없으면 서버는 모든 토큰을 무료로 본다.

### 구글이 "User location is not supported" 라고 하면

Worker 는 사용자 근처 데이터센터에서 돌고, 한국 통신사 트래픽은 홍콩 센터에 붙는 일이
잦다. 구글은 홍콩 IP 를 거절한다. 그래서 구글 호출은 `GoogleRelay`(Durable Object,
위치 힌트 `enam`) 안에서만 한다. 이 오류가 다시 보이면 그 객체가 다른 곳에 만들어진
것이다 — `RELAY_NAME` 을 바꿔 새 객체를 만들면 힌트가 다시 먹는다.

### 알아 둘 구멍

- 설치 ID 는 지우고 다시 깔면 새로 난다 → 무료 5 회도 새로 난다. IP 한도(하루 300)가
  한 번 더 거른다. 제대로 막으려면 Play Integrity 나 로그인 — 아직 그럴 가치가 없다.
- Play 확인 결과를 1 시간 캐시하므로 해지 후 그만큼은 더 쓸 수 있다.
- D1 무료 등급: 하루 쓰기 10 만 건. 교정 한 번에 쓰기 두 번(설치 ID, IP).
- Billing 라이브러리 7.1.1 의 `PendingPurchasesParams` API 는 이 컨테이너에서 컴파일해
  보지 못했다(AGP 차단). CI 가 첫 검증이다.

## 키보드 모양 설정 (2026-09-12)

- **테마**: `ThemeMode`(밝게/어둡게, 시스템 따라가기는 요청으로 뺌) → `KeyboardTheme.current()`.
  키보드 색은 전부 이 객체에서 나온다. 리소스 ID 를 직접 꺼내 쓰지 말 것.
- **배경 사진**: 설정에서 고르면 `BackgroundImage.save()` 가 줄여서 `files/keyboard_background.jpg`
  에 둔다. 키보드는 `applyAppearance()` 에서 파일 수정 시각이 바뀐 경우에만 다시 푼다.
  사진 위에서는 키가 86% 불투명, 상단 문구엔 반투명 바탕.
- **실시간 교정 토글**: 자판 도구 줄 '교정' 버튼 ↔ 설정 스위치, 둘 다 `Prefs.autoCorrectEnabled`.
  버튼은 지금 입력란에 즉시 먹는다(`session.correctionEnabled`).
- **스페이스 꾹 → 커서 이동**: 스페이스는 다른 키와 달리 **뗄 때** 들어간다(`attachSpaceTouch`).
  380ms 누르면 커서 모드, 18dp 마다 한 글자, 서비스는 DPAD 키 이벤트로 옮긴다.
- **톤**: 키 아래 1dp 그림자(`keyFace`), 바탕 #E8EAEE, 키 48dp/틈 3dp/줄 간격 5dp, 도구 줄은 단색 기호.

## 천지인 · 토스 톤 설정 화면 · API 칸 제거 (2026-09-12)

- **천지인**: `core/hangul/CheonjiinAutomata` (JVM 테스트 18개). 모음은 ㅣㆍㅡ 획 열로 들고
  있다가 접는다(`VOWEL_TRANSITIONS`). 자음 연타(ㄱ→ㅋ→ㄲ)는 `press(key, repeat=true)` 로
  받고, "같은 키를 700ms 안에" 는 서비스가 잰다(`MULTI_TAP_MS`). `.,?!` 키도 같은 창으로
  돈다. 자판은 전화기 3×4 + 오른쪽 기능 열(⌫ ↵ 스페이스 한/영). 설정 → 키보드 → 자판.
  `TypingSession.automata` 로 조립기를 갈아 끼운다(`JamoAutomata` 인터페이스).
- **설정 화면**: 카드/행/알약/분할 선택은 `values/styles.xml`, 색은 `toss_*`(밤 값은
  `values-night`). 시작하기 카드는 시스템에 물어 "완료" 를 표시한다. 문제 해결 카드는 접혀 있다.
- **API 칸 제거**: 사용자 키·모델 칸과 그 코드 경로(`Prefs.userApiKey/model`)를 뺐다. AI 는
  언제나 중계 서버, 모델은 `DEFAULT_MODEL` 에서 시작해 교정기가 스스로 갈아탄다.
- **사진 위 키**: 30% 불투명.

## 천지인 버그·삼성 기호·클립보드 격자 (2026-09-12)

- **천지인 안 모아짐 고침**: 천지인 낱자 키는 `onChar` 가 아니라 전용 `onCheonjiinKey` 로
  보낸다. onChar 는 자판을 `session.automata` 동일성으로 되판별했는데, 그게 어긋나면
  점(ㆍ)이 두벌식 경로에서 그냥 글자로 박혀 모음이 안 생겼다. 뷰가 이미 천지인 키라고
  알고 있으니 다시 판별하지 않는다.
- **삼성 기호 자판**: `KeyboardLayout.SYMBOL_PAGES` 두 페이지(각 10·10·10 + 특수 7).
  `renderSymbols()` 가 [1/2·특수·⌫] 줄과 바닥 기능 줄을 그린다. `KeyAction.SYMBOL_PAGE`.
- **클립보드**: 2열 카드 격자(`clipboardCard`), 카드 눌러 붙여넣기, 오른쪽 위 ✕ 로 삭제.

## 삼성식 천지인 판·이모티콘·키 씹힘 (2026-09-12)

- **천지인 판**: 한글(숫자 힌트, 길게 누르면 숫자) / 숫자 판(`KeyboardMode.NUMPAD`) /

- **키 씹힘 대책 셋**: (1) 스페이스를 잡고 있는 동안 다른 키가 눌리면 스페이스를 먼저 넣는다

## API 비용 (2026-09-12)

- 요청 하나의 비용 = 보내는 글자(지시문 ~300토큰 + 본문) + 돌아오는 글자(본문과 같은 길이) +

  `GET /stats` → `{days:[{day, requests, prompt, output, thoughts}]}` (최근 31일).
  `thoughts` 가 0 이 아니면 어딘가에서 숙고가 켜진 것이다.
- **한도 되돌리기**: Actions → "Reset AI usage" → Run workflow. 오늘(KST) `usage` 행을 지운다.
  테스트하다 무료 5회를 다 썼을 때. 서버·앱 코드와 무관.

## 천지인 "다음" 키·키 씹힘·키 투명도 (2026-09-12)

> "다음" 키는 다음 절에서 없앴다. 스페이스가 그 일을 겸한다.

- **천지인 "다음" 키**: 바닥 줄 오른쪽(예전 쉼표 자리). 조합 중인 글자만 끝내고 아무것도
  넣지 않는다(`KeyAction.NEXT_CHAR`). "안녕" 처럼 받침 ㄴ 뒤에 초성 ㄴ 이 올 때 700ms 를
  기다리지 않아도 된다. 쉼표는 오른쪽 `.,?!` 키에서 나온다.
- **키 씹힘의 확인된 원인 하나**: 터치 처리가 `ACTION_POINTER_DOWN` 을 안 받고 있었다.
  손가락 하나가 키에 남아 있는 채로 두 번째 손가락이 같은 키에 닿으면 DOWN 이 아니라
  POINTER_DOWN 이 오는데, 그 입력이 조용히 사라졌다. POINTER_DOWN/UP 을 DOWN/UP 과 같이
  다룬다. 빠르게 칠수록 자주 났다.
- **키 투명도**: 설정 → 키보드 → 배경 사진 아래 슬라이더(0~100, 기본 70).
  `Prefs.keyTransparency` → `KeyboardView.alphaFor`. 배경 사진이 있을 때만 쓰인다.

## 키보드 전체가 키 · 스페이스가 "다음 글자" 겸함 (2026-09-12)

### 키 씹힘의 진짜 원인: 키 사이 여백이 아무 키도 아니었다

사용자가 삼성 키보드와 비교해 찾아냈다. **삼성은 자판 바닥 전체가 키다** — ㅅ과 ㅎ
사이의 빈틈을 누르면 가까운 쪽이 눌리고, 줄 맨 끝 키(ㅁ, ㅣ)는 화면 가장자리까지가
제 영역이다. 우리는 키 뷰마다 `OnTouchListener` 를 달아서 그 여백(키 사이 3dp, 판
둘레 2~6dp)이 어느 키도 아니었고, 거기 떨어진 손가락은 아무 일도 하지 않았다.
빠르게 칠수록 손가락이 키 한가운데에 정확히 떨어지지 않으니 자주 났다.

고친 방법 — 손가락 배분을 뷰에서 판으로 옮겼다(`KeyboardView.kt`):

- `KeyPad`(`rowContainer`)가 `dispatchTouchEvent` 를 가로채 자식에게 내려보내지 않는다.
- 키를 만들 때 뷰에 리스너를 달지 않고 `addPadKey` 로 `keySlots` 에 등록한다.
  자판을 다시 그릴 때(`render`) 목록을 비운다.
- `slotAt(x, y)` 가 점을 품은 키를 주고, 없으면 **가장 가까운** 키를 준다. 여백은
  자연히 양쪽 키의 한가운데에서 갈린다.
- `activeSlots`(손가락 id → 키)로 여러 손가락을 따로 추적한다. `ACTION_DOWN` 이면
  남아 있는 항목은 놓친 것이므로 전부 취소한다(⌫ 반복이 멎지 않던 경우 대비).
- 판 둘레 여백을 바깥(`KeyboardView` 의 padding)에서 **판 안쪽** padding 으로 옮겼다.
  그래야 화면 맨 아래·좌우 가장자리도 판이 받는다. 도구 줄과 두 패널은 같은 크기의
  padding 을 스스로 갖게 해서 생김새는 그대로다.
- 터치 처리 코드는 `KeyTouch`(down/move/up/cancel) 로 묶었다. 자판 밖의 키(도구 줄,
  이모티콘 칸, 클립보드 칸)는 그대로 뷰마다 리스너를 단다 — 드문드문 있어서 "가까운
  것을 누른 것으로 친다" 가 오히려 해롭다.

### 천지인 "다음" 키를 없애고 스페이스에 합쳤다

원래 천지인이 그렇다: 조합 중에 스페이스를 누르면 글자가 끊기고, 한 번 더 누르면
그때 띄어쓰기다. `KeyAction.NEXT_CHAR` 와 "다음" 키는 지웠고(쉼표가 제자리로 돌아옴),
`SpellKeyboardService.onAction` 의 `KeyAction.SPACE` 가 천지인이면서 조합 중일 때만
`commitPending` 을 한다. `onAction` 첫머리에서 `lastTapKey` 를 비우므로, 끊은 뒤
같은 키를 바로 눌러도 연타(ㄴ→ㄹ)가 아니라 새 글자가 된다.

## AI 모델을 gpt-5-nano 로 (2026-09-12)

### 왜

gemini-3.5-flash-lite 는 출력 100만 토큰에 **$2.50**, gpt-5-nano 는 **$0.40** 이다.
맞춤법 교정은 원문을 통째로 다시 뱉는 일이라 출력이 요금의 8할이고, 그래서 바꾸는
것만으로 요금이 **6분의 1** 이 된다. 교정은 판단이 아니라 패턴이라 nano 로 충분하다.

조사한 것들(2026-09 기준, 입력/출력 100만 토큰당): Gemini 3.5 Flash-Lite $0.30/$2.50,
Gemini 3.1 Flash-Lite $0.25/$1.50, **GPT-5 nano $0.05/$0.40**, Qwen3.7 Flash $0.03/$0.13,
DeepSeek V4 Flash $0.12/$0.35, 하이퍼클로바X DASH ₩0.001/토큰. Qwen 이 제일 싸지만
키보드에 치는 모든 글이 중국 업체로 가는 것이 걸려서 뺐다. GPT-5.4 nano 는 $0.20/$1.25
로 오히려 비싸다.

한 달 요금(2,000자 × 하루 150회 기준): 41,784원 → **6,721원**.

### 어떻게 — 앱은 그대로 두고 서버에서 번역한다

이미 깔린 APK 들은 구글 모양으로 보내고 구글 모양 응답을 읽는다. 그래서 번역을
서버에 뒀다. **앱을 다시 깔지 않아도 적용된다.**

- `server/src/openai.js` (새 파일): `toOpenAiRequest` / `toGeminiReply` / `modelList`.
- `server/src/index.js`: `OPENAI_API_KEY` 비밀값이 있으면 OpenAI, 없으면 예전처럼 구글.
  **되돌리기는 비밀값 하나 지우는 것**이다.
- 앱이 보낸 모델 이름은 쓰지 않는다. 무엇으로 고칠지는 서버가 정한다
  (`OPENAI_MODEL` 환경변수로 바꿀 수 있고, 기본은 `gpt-5-nano`).
- `/v1beta/models` 는 물어보지 않고 쓰는 이름 하나만 돌려준다.

주의해서 다룬 것들:

- **잘린 답은 주지 않는다.** 앱은 받은 글로 입력란을 통째로 덮으므로, `finish_reason`
  이 `length` 면 502 로 실패시킨다. 안 그러면 사용자 글의 뒷부분이 사라진다.
- **출력 한도를 넉넉히 준다.** OpenAI 는 숙고 토큰도 `max_completion_tokens` 에서
  깎는다. 앱이 부른 4096 을 그대로 주면 긴 글에서 잘린다. 2배로 주되 2048~16384 로 자른다.
- **temperature 를 안 보낸다.** gpt-5 계열은 이 항목을 받으면 400 이다.
- **`reasoning_effort: 'minimal'`**. 거절당하면 빼고 한 번 더 보낸다(앱이 구글의
  thinkingBudget 에 하던 것과 같은 수법).
- **토큰 집계**: OpenAI 의 `completion_tokens` 에는 숙고가 들어 있고 구글의
  `candidatesTokenCount` 에는 없다. 빼서 넣어야 `/stats` 가 두 번 세지 않는다.
- 중계 Durable Object(`enam` 고정)는 그대로 쓴다. OpenAI 도 홍콩을 지원 지역에서 뺐다.
- 개인정보 처리방침 페이지와 앱의 고지 문구를 "OpenAI" 로 바꿨다. 방침 페이지는
  실제 설정을 따라가므로 구글로 되돌리면 문구도 같이 돌아간다.

### 남은 일

사용자가 OpenAI 키를 만들어 GitHub 비밀값 `OPENAI_API_KEY` 에 넣고 "Deploy AI server"
를 돌려야 한다. 그 전까지는 서버가 예전처럼 구글로 간다.

다음 단계(더 큰 절감): 지금은 고친 문장 **전체**를 다시 뱉게 한다. 바뀐 부분만
내보내게 하면 출력이 1/5~1/10 로 준다. 모델 교체와 곱해져 지금의 30~50분의 1이 된다.

### 품질 보정 1차 (2026-09-12)

실기기에서 "예전 Gemini 는 100%, gpt-5-nano 는 95% 쯤" 이라는 평가가 나왔다. 원인 셋:

1. **온도를 못 낮춘다.** Gemini 에는 `temperature: 0` 을 줬는데 gpt-5 계열은 이 항목을
   받으면 400 이다(기본값 1 고정). 답이 매번 조금씩 흔들린다. 직접 고칠 수단이 없어
   지시문으로 누르는 수밖에 없다.
2. **지시문이 짧았다.** 큰 모델은 규칙 한 줄로 알아듣지만 작은 모델은 예시를 봐야 안다.
3. **숙고를 완전히 껐다.** `minimal` → `low`.

고친 것:

- **지시문을 서버로 옮겼다**(`KO_SYSTEM_PROMPT`, 1,278자 ≈ 1,534토큰). 앱이 보낸 지시문은
  쓰지 않는다. 앞으로 프롬프트를 손볼 때 APK 를 새로 깔 필요가 없다 — 배포 한 번이다.
  되돌리려면 `OPENAI_PROMPT=app`.
- 지시문을 길게 쓴 것은 낭비가 아니다. 입력은 출력의 8분의 1 값이고, 1024 토큰이 넘는
  같은 앞부분은 OpenAI 가 **90% 깎아 준다**(캐싱, $0.005/1M). 그래서 문턱을 넘겨 두었다 —
  테스트가 이 길이를 지킨다.
- 지시문에 한국어 오류 유형별 예시 12개. "왜케" 같은 줄임말을 고치지 말라는 것을
  **예시를 한 번 틀리게 보여 준 뒤 바로잡는** 식으로 넣었다. 작은 모델에 잘 먹는다.
- `reasoning_effort` 기본 `low`, `OPENAI_REASONING` 으로 바꿀 수 있다.

값은 거의 그대로다(최악 월 6,721원 → 7,215원). 이래도 모자라면 `OPENAI_MODEL=gpt-5-mini`
($0.13/$1.00)로 한 단계 올린다 — 그래도 예전 Gemini 보다 2.5배 싸다.

### 품질 보정 2차 — 단어를 바꿔 버리는 실패 (2026-09-12)

띄어쓰기를 전부 없앤 문단으로 시험했더니 세 군데가 틀렸다.

| 원문 | 나온 것 | 판정 |
|---|---|---|
| 일처리 | 일처리 | 못 고침 |
| 들은바에**의하면** | 들은 바에 **따르면** | **단어를 바꿈** |
| **오죽**하겠냐마는 | **어쩜 하**겠냐마는 | **없는 말을 지어냄** |

띄어쓰기 복원 자체는 문단 전체를 거의 완벽하게 해냈다. 문제는 그 과정에서 글자가
바뀐다는 것이다. 지시문에 "의미·단어를 바꾸지 마라" 는 있었지만 **띄어쓰기를 다시
나누는 동안에도 글자가 보존돼야 한다** 는 말은 없었다. 모델은 그 둘을 다른 일로 본다.

- 지시문에 "절대 규칙: 없는 글자를 만들지 마라" 절을 넣었다. 공백을 빼면 입력과 출력의
  글자가 같아야 한다는 것, 그리고 위 두 실패를 ○/✗ 로 짝지어 보여 준다.
- "모르는 말일수록 그대로 둔다. 모르는 말은 틀린 말이 아니다." 를 못박았다.
- 실패한 문장 두 개를 예시로 그대로 넣었다.

**길이 안전장치**(`tooDifferent`): 교정문의 공백 뺀 길이가 원문의 60% 미만이거나 160%
초과면 502 로 막는다. 20자 미만은 재지 않는다. 조금 틀린 교정이 아니라 **교정이 아닌
것**(요약, 본문 속 지시문 따라가기, 사용자 질문에 대답하기)을 걸러내는 그물이다.
프롬프트 주입이 뚫렸을 때의 마지막 방어선이기도 하다.

지시문이 백틱 문자열이라 안쪽에 백틱을 넣었다가 한 번 깨뜨렸다. 테스트가 지킨다.

**남은 문제**: 단어 치환이 프롬프트로 안 잡히면 모델을 올려야 한다
(`OPENAI_MODEL=gpt-5-mini`, $0.13/$1.00 — 그래도 예전 Gemini 보다 2.5배 싸다).
지시문으로 잡히는지 먼저 확인할 것.

### 모델을 gpt-5-mini 로 올렸다 (2026-09-12)

nano 가 띄어쓰기를 다시 나누다 단어를 지어내는 문제(위 2차 참고)를 지시문으로 눌러
봤지만, 모델이 작아서 생기는 일이라 한계가 있다고 보고 한 단계 올렸다.
`wrangler.toml` 의 `OPENAI_MODEL = "gpt-5-mini"` 한 줄이다. 되돌리려면 nano 로 고친다.

값(지시문 2,681 토큰 · 캐싱 적용 · 환율 1,350원 기준):

| | 예전 Gemini | nano | **mini** |
|---|---|---|---|
| 500자 5번 | 21원 | 3원 | **6원** |
| 하루 30번(300자) 한 달 | 2,961원 | 335원 | **840원** |
| 하루 150번(2000자) 한 달 | 49,507원 | 7,250원 | **18,206원** |

구독료 2,990원 본전: 2,000자짜리 하루 24.6회, 300자짜리 하루 107회.

**"최악" 이 무엇을 말하는가**: 사용자가 제안한 한도(1회 2,000자 · 하루 150회)를 한 사람이
30일 내내 **꽉 채워** 썼을 때다. 예보가 아니라 **천장**이다 — 한 사람이 하루도 빠짐없이
A4 한 장짜리 글을 150번 고쳐야 나오는 숫자이고, 정상 사용자는 근처도 못 간다. 한도를
정할 때 "최악이 얼마까지 벌어지나" 를 재는 자리에만 쓴다.

### 시험용 한도 (2026-09-12) — 출시 전에 되돌릴 것

`FREE_DAILY_LIMIT` 를 5 → **200** 으로 올렸다. 시험하다 하루 5회를 계속 다 써서다.

**출시 전에 5 로 되돌려야 한다.** 무료 5회가 구독을 사게 만드는 장치다.

`IP_DAILY_LIMIT` 은 300 그대로 뒀다. 서버 주소는 APK 에 들어 있어 누구나 알 수 있으므로
실제 요금 천장은 이쪽이고, 무료 한도를 올려도 **한 IP 가 쓸 수 있는 총량은 변하지 않는다**
(한 IP 가 하루 300회를 2,000자로 꽉 채워야 1,137원/일). 그래서 이 변경으로 늘어난 위험은
없다.

나중에 할 것: 시험용 설치 ID 를 무제한으로 봐 주는 목록(`TESTER_INSTALL_IDS`)을 두면
무료 한도를 건드리지 않고도 내부 테스트를 할 수 있다. Play 내부 테스트 때 필요해진다.

### IP 한도 300 → 2,000 (2026-09-12)

학교·회사 와이파이와 통신사 NAT 뒤에는 폰 수백 대가 IP 하나를 같이 쓴다. 300 이면 한
건물에서 앱이 퍼지는 순간 뒤에 온 사람이 아무 잘못 없이 막힌다. 2,000 이면 한 건물
500명이 매일 5회를 꽉 채워야 걸리고, 스크립트 공격은 여전히 하루 7,400원에서 막힌다.
구독자는 이 검사를 거치지 않는다.

막혔을 때 문구를 "이 네트워크에서 오늘 무료 사용이 많았습니다 … 구독하면 제한 없이"
로 바꿨다(`GeminiCorrector.explain`). 잘못한 게 없는 사람이 보는 문구라 나무라면 안 되고,
그 자리가 결제 지점이다.

근본 해법은 Play Integrity — IP 를 보지 않고 "진짜 기기·진짜 설치" 를 구글이 보증한다.
10만 명이 넘거나 캠퍼스 단위로 퍼지기 시작하면 그때 한다.

### 한도 설계 결론 (2026-09-12)

| | 1회 길이 | 하루 횟수 | 한 명 최악(월) | 현실적(월) |
|---|---|---|---|---|
| 무료 | 2,000자 | 5회 | 556원 | 27원 |
| 구독 | 2,000자 | 50회 | 5,562원 | 234원 |

- 길이는 무료·유료 같다. 길이를 자르면 긴 글에서 앞부분만 고쳐지고 사용자는 모른다.
- 무료 5회는 비용이 아니라 **구독을 파는 장치**다.
- 구독 50회는 사람 감각에 무제한이면서 최악을 막는 천장이다. 500자 기준으로 환산하면
  같은 돈으로 193회라, 짧게 쓰는 사람은 손해지만 1버전은 단순하게 간다.
- **아직 구현 안 됨**: 서버는 구독자를 아예 세지 않는다(`if (!subscriber)`). 50회 한도는
  코드가 필요하다. 그리고 앱 문구 "월 2,990원으로 무제한 쓰기" 를 "하루 50회" 로 바꿔야
  한다 — 한도를 걸면서 무제한이라 쓰면 거짓 광고다.

### 요금제 확정: 무료 하루 5회, 프리미엄 하루 10만 자 + 결제 화면 (2026-09-12)

| | AI 전체 교정 | 실시간 교정 |
|---|---|---|
| 무료 | 하루 **5회** (길이 무관, 1회 최대 2,000자) | 무제한 |
| 프리미엄 월 2,990원 | 하루 **10만 자** | 무제한 |

**구독자는 횟수가 아니라 글자 수로 센다.** 요금이 글자 수에 붙기 때문이다(교정문이 원문만큼
나온다). 횟수로 세면 카톡 한 줄과 A4 한 장이 같은 값이 되고 어느 쪽에 맞춰도 한쪽은 손해다.
10만 자면 100자짜리 1,000번, 300자 333번, 500자 200번, 1,000자 100번, 2,000자 50번.
호출당 최소 50자로 쳐서 한 글자짜리를 만 번 보내는 것이 공짜가 되지 않게 했다.
최악(하루 10만 자를 30일) 5,500~6,900원, 현실적 구독자 234원. 수수료 10% 뗀 수입 2,691원.

- 서버(`quota.js` `chargeFor`/`decideChars`, `index.js`): 구독자는 `chars:<installId>` 키로
  `usage` 에 글자 수를 쌓는다(`bumpBy`). `SUB_DAILY_CHARS` 환경변수(기본 100,000). 넘으면
  402 `sub_daily_limit`. 헤더 `x-quota-unit`(calls/chars)로 단위를 알려 준다 — 옛 앱은 이
  헤더가 없으면 횟수로 읽는다. 구독자는 IP 한도를 거치지 않는다.
- 앱: `Quota.unit`/`countsChars`, 상태 줄 "오늘 87,000자 남음", 설정 "프리미엄 · 오늘 N자 남음",
  `explain()` 에 `sub_daily_limit`. "무제한" 이라는 말은 전부 뺐다 — 한도를 걸면서 무제한이라
  쓰면 거짓 광고다.
- **결제 화면 `PaywallActivity`**(`activity_paywall.xml`): 설정의 프리미엄 버튼이 결제창을 바로
  띄우지 않고 이 화면을 연다. 헤드라인 "하루에 99원으로 삶의 질을 높여보세요!"(2,990원 ÷
  30.4일 = 98.4원), 무료/프리미엄 비교표, "10만 자면 이만큼" 표(코드로 채움, `DAILY_CHARS` 는
  서버 값과 같아야 한다), CTA 가 `BillingManager.subscribe`. 구독 확인되면 1.5초 뒤 닫힌다.
  설정 화면은 `onResume` 에서 요금 상태를 다시 그린다.

주의: `FREE_DAILY_LIMIT` 은 아직 **시험용 200** 이다. 출시 전 5 로.

### 디코더가 고르는 방식 (ContextCorrector)

점수(가설) = Σ ln P(어절 | 앞 어절) + 통로 비용. 원문 가설보다 `MARGIN`(1.5) 이상 좋아야 고친다.
- 언어모델: 바이그램과 유니그램의 **보간** (`lnConditional`). 연쇄를 봤다는 이유만으로 점수가 무한정 벌어지지 않게.
- 모르는 어절: 사전이 나누거나 분석이 안 되면 음절마다 −4.5 (여러 어절이 붙은 것), 무리 없이 분석되면
  거의 안 깎음 (드문 낱말일 뿐 — '대문만이', '닮을'), 그 사이는 음절마다 −2.5.
- 아는 어절이라도 한 어절로 분석이 안 되면 −5 (`usagePenalty`: '할수있다').
- 편집: 헷갈리는 자모끼리만 (ㅐ/ㅔ 1.0, ㅅ/ㅆ 받침 0.8, 된소리 1.8 …) + 기본 1.5 + 원문이 흔할수록 더
  (`knownPenalty`, 빈도 20 넘는 만큼 ln 당 1.0). ㅢ 는 뺐다 ('의'→'이/에'가 늘 그럴듯해 보여서).
  **모르는 말끼리의 편집은 안 한다** (이름·외래어가 망가진다).
- 붙이기: 지운 자리에 매인 형태소(조사·어미·접미사)가 시작할 때만, 비용 −3, 붙인 말이 빈도 100 이상.
  '안녕 하세요'·'먹었 어요' 는 되고 '와 봐' 는 안 된다.
- 나누기 (사전이 나눈 자리): 명사|명사는 두 조각 연쇄가 33번 넘게 보였을 때만, '-아/어'|용언·체언|받다 는
  안 나눔 (둘 다 맞는 표기). 조사·어미로도 읽히는 한 음절('어', '가')은 떼지 않음.
- 나누기 (언어모델만 근거): 한 어절로 무리 없이 분석되면 안 나눔, 두 조각 연쇄가 있어야 함, 매인 형태소
  앞·명사|명사·'-아/어'|용언·체언|받다 자리는 안 나눔.

`ContextCorrector.explain(창, 앞어절)` 이 왜 그렇게 골랐는지 점수를 풀어 준다. `LmDiagnosticsTest` 가
표본을 찍는다 (`./gradlew -p <scratch>/coretest :core:test --tests '*LmDiagnosticsTest' -i`).

### 형태소 분석 제약을 늘렸다 (Spacer)

mecab-ko-dic 에는 '은'·'가'·'할'·'제가'(諸家) 같은 한 음절 명사가 잔뜩 있어서 웬만한 덩어리는 명사
나열로 억지 분석된다. 그래서 (1) 접미사는 체언 뒤에만, (2) 어미는 용언·서술격조사 뒤에만, (3) 한 어절
판정(allowSpaces=false)에서는 연결어미 뒤 용언과 체언 뒤 '받다·당하다·시키다·드리다' 를 붙여 둔다.
NNBC(단위 의존명사)·XSN 을 체언으로 친다. `boundMorphemeStartsAt/edgeTags/tagAt` 는 형태소당 비용이
2000 을 넘는 억지 분석은 믿지 않는다 (`BOUND_TRUST_COST_PER_MORPH`).

### 측정 (`EvaluationTest`, `SPELL_EVAL_FILES=<xnli.dev.ko.tsv>,<xnli.test.ko.tsv>` 로 켠다)

말뭉치 밖 문장(KorNLI dev/test 2,000개, 격식체 번역문):

| 지표 | 1차 (규칙 없이 디코더만) | 최종 |

| 띄어쓰기 하나 지운 것 복원 | 76.9% | 64.0% (합성어·보조용언은 일부러 안 나눔) |
| ㅐ/ㅔ 하나 바꾼 것 복원 | — | 72.6% |
| 창 하나 처리 시간 | | 1.0ms |

남은 오교정 넷은 '군데에서→군대에서'(둘 다 흔한 말, 문맥이 약함), '미국인치고는→미국인 치고는'
(mecab 이 '치고'를 조사로 못 봄), 이름 조각 둘. 채팅 문장 44개 표본은 셋만 고쳤고('가는 중',
'안녕히 계세요', '살게') 나머지는 그대로 뒀다 — 은어·신조어 손대지 않음.

사용자 세 문장: '여기 있는데요' ✓ (차이 2.25), '뭐 하세요' ✓ (15.2), '아버지 가방에 들어가신다' 는
**그대로 둔다** — 문법적으로 맞는 문장이고, 언어모델도 '아버지가 방에' 를 더 좋아하지 않는다
(둘 다 드문 연쇄). 이건 의미를 알아야 하는 문제라 AI 버튼의 몫이다.

- 문턱·비용은 전부 `ContextCorrector` companion 의 상수. 바꾸면 `EvaluationTest` 로 오교정률부터 본다.
  **오교정 1% 를 넘기면 안 된다.**
- 유니그램 문턱을 3 으로 내리면 '제가할게요' 같은 오타가 "아는 말" 이 돼 못 고친다. 5 로 둔 이유.
- 말뭉치를 더 구하면 (특히 구어 바이그램) `count_ngrams.py` 의 `texts()` 에 읽기만 보태면 된다.
- 1세대 부품(`Spacer.space` 직접 호출, `Speller`)은 언어모델을 못 열었을 때의 대비책으로 남아 있다.

## 실시간 번역 입력줄 — 온디바이스 (2026-09-13)

사용자가 고른 것: 서버 LLM 이 아니라 **기기 안에서** 도는 번역. 구글 ML Kit 번역
(`com.google.mlkit:translate:17.0.3`)을 쓴다. 언어팩(언어당 약 30MB)은 처음 쓸 때 기기가
내려받고, 그 뒤로는 네트워크·서버 비용·AI 한도 없이 돈다.

### 모양 (지보드 방식)

도구 줄의 '번역' 동그라미를 누르면 자판 위에 입력줄이 열린다. 거기 한국어를 치면 **앱 입력란에는
번역문이** 들어가고, 글자를 더 치거나 지우면 번역문이 갈아 끼워진다. 오른쪽 언어 칩('영어 ▾')을
누르면 영어→일본어→중국어로 돈다. 엔터는 번역문을 그대로 보내고(앱의 전송 동작), ✕ 는 번역문을
남긴 채 입력줄만 닫는다.

### 부품

| 파일 | 역할 |
|---|---|
| `core/.../editor/TranslateBuffer.kt` | 입력줄의 `Editor`. 키 입력·한글 조합·자동 교정이 이 위에서 평소처럼 돈다. `TranslationOutput` 은 앱 입력란에 넣은 번역문 길이를 기억했다가 갈아 끼운다 |
| `keyboard/.../OnDeviceTranslator.kt` | ML Kit 감싸개. `TargetLanguage`(영·일·중), 언어팩 확인/다운로드, 번역 |
| `SpellKeyboardService` | `translating` 이면 `editor()` 가 `translateBuffer` 를 돌려준다 — 모든 키 경로가 그걸 거치므로 여기 한 군데로 갈린다. 내용이 바뀌면 250ms 뒤 번역, 요청 번호로 늦은 결과 폐기, 엔터는 최신 번역이 들어간 뒤에만 보냄 |
| `KeyboardView` | '번역' 동그라미(켜지면 강조색), 입력줄 패널(`setTranslateMode/setTranslateSource`) |

### 알아 둘 것

- 자동 교정이 번역 전에 한국어를 고친다 — '안녕하새요' 를 치면 '안녕하세요' 로 고쳐진 뒤 번역된다.
- 번역 모드에서 AI 교정 버튼은 막아 뒀다 (입력란에 든 건 번역문이라 고칠 대상이 아니다).
- 입력란이 바뀌거나(`onStartInput`) 키보드가 내려가면(`onFinishInput`) 모드가 풀린다.
- ML Kit 은 이 컨테이너에서 컴파일할 수 없다(구글 메이븐 차단). 검증은 CI 뿐이다. API 이름은
  공식 문서대로 썼다: `Translation.getClient(TranslatorOptions)`, `downloadModelIfNeeded(DownloadConditions)`, `translate(text)`.
- 원문 언어는 한국어로 고정. 영어 자판으로 영어를 치면 엉뚱한 결과가 나온다 — 지보드도 같다.

### 문장 단위 번역 (첫 실기기 확인 뒤 고친 것)

실기기 첫 시도에서 네 문장을 치니 두 문장이 나왔다:

    안녕하세요 저는 김건우입니다 오늘 기분이 어떠세요? 저는 좋아요
    → Hello, I am Kim Kun-woo? I like it.

가운데 문장이 통째로 사라지고 물음표만 앞 문장에 붙었다. 교정 엔진은 저 문장들을 하나도
건드리지 않으므로(진단으로 확인) 원인은 번역기다 — **ML Kit 은 문장 하나를 번역하는 작은
모델이라 여러 문장을 한 번에 던지면 중간을 삼킨다.**

- `core/.../translate/SentenceSplitter.kt` — 문장 부호·줄바꿈·**종결어미**·길이(80자)로 자른다.
- `core/.../translate/TranslationMemory.kt` — 문장별 번역을 기억한다. 끝에만 글자가 붙으므로
  앞 문장은 다시 번역하지 않는다(빠르고, 앞쪽 영어가 흔들리지 않는다).
- `Spacer.endsWithFinalEnding` — 한국어 채팅은 마침표를 안 쓰므로 부호 없이 문장 끝을 찾아야
  한다. **mecab-ko-dic 은 종결어미를 대부분 연결어미와 같은 EC 로 태깅한다** ('좋아요'도
  '좋아서'도 EC). 그래서 EF 태그는 그대로 믿고, EC 면 어미 표층형(`요 다 까 죠 네 군 구나 자`)을
  본다. 반말 종결('먹었어', '그래')은 연결형('좋아 보여')과 꼬리가 같아 일부러 뺐다 —
  문장 둘이 붙는 손해가 한 문장을 잘못 자르는 손해보다 작다.

번역 실패한 문장은 원문을 그대로 남긴다. 그 자리가 비면 사용자는 글이 사라진 줄 안다.

### 글자가 지워지던 버그 (꼭 알아 둘 것)

두 번째 실기기 확인에서 '어' 를 쓰고 'ㄸ' 를 누르면 '어' 가 사라졌다. 원인은 번역이 아니라
**`onUpdateSelection`** 이었다.

번역문을 앱 입력란에 써 넣으면 앱이 커서 알림을 돌려준다. 그 알림을 "사용자가 커서를
옮겼다" 로 읽고 `session.reset()` 을 하는 방어 코드가 있는데(빠른 타자에서 조합이 깨지는 것을
막으려고 넣은 것), 자기 편집으로 치는 창이 `SELF_EDIT_WINDOW_MS = 200ms` 인 반면 번역은
타이핑이 멎고 **250ms** 뒤에 돈다. 그래서 번역할 때마다 창 밖이라 판정돼 조합이 끊겼고,
끊긴 뒤 자모를 누르면 `TranslateBuffer` 에 남은 옛 조합 자리가 앞 글자를 덮어썼다.

고친 것: 번역 모드에서는 `onUpdateSelection` 을 통째로 무시한다 — 사용자는 앱 입력란이
아니라 입력줄에 쓰고 있고, 앱 입력란이 바뀌는 것은 우리가 번역문을 갈아 끼울 때뿐이다.
`TranslateBuffer` 도 어긋난 조합 자리를 스스로 버리게 했다. 회귀 테스트는
`TranslateBufferTest` 에 있다.

**입력줄과 조립기는 늘 함께 비워야 한다.** 하나만 비우면 조립기에 남은 '어' 가 다음 'ㄱ' 과
합쳐져 '억' 이 된다.

### 품질 올리기 — 번역기에 먹이는 것을 바꾼다 (2026-09-13)

ML Kit 모델은 못 바꾼다. 대신 **무엇을 먹이고 무엇을 안 먹이느냐**로 올린다. 셋을 넣었다.

1. **`ChatText`** — 채팅 한국어를 문장다운 문장으로 다듬는다. 번역기는 마침표가 있고
   'ㅋㅋ' 가 없고 글자가 늘어지지 않은 문장으로 배웠는데, 채팅은 셋 다 어긋난다.
   - 마침표가 없으면 붙인다. 의문형 어미(`-까 -나요 -니 -냐 …`)거나 **의문사가 한 어절로**
     들어 있으면 물음표 — 종결어미만으로는 못 가린다('좋아요'와 '어떠세요'가 둘 다 '요').
     의문사는 어절 통째로 맞을 때만 센다('왜냐하면'의 '왜'에 안 걸리게).
   - 'ㅋㅋㅋ'·'ㅠㅠ' 를 떼어 내고 번역 뒤에 그 언어의 말로 붙인다(lol / (笑) / 哈哈).
     'ㅇㅇ'·'ㄴㄴ' 처럼 **뜻이 있는** 줄임말은 떼지 않는다 — 관용구 표가 옮긴다.
   - 늘여 쓴 글자를 줄인다. '좋아아아아'→'좋아'. 늘임소리가 앞 글자의 모음을 늘인 것이면
     (초성 ㅇ, 받침 없음, 같은 모음) 통째로 버린다 — '네에에에'→'네'.
2. **`Phrasebook`** — 자주 쓰는 채팅 문장 ~170개(영)·~70개(일·중)를 손으로 옮겨 뒀다.
   열쇠는 **공백을 뺀 문장**이라 '뭐 해'와 '뭐해'가 한 줄로 덮인다. 표에 없으면 모델로
   넘어가므로 손해가 없다. 실기기에서 나온 '저는 좋아요' → "I like it" 이 여기서 잡힌다.
3. **문장 부호 현지화** — 일본어·중국어는 `。？！` 를 쓴다.

표를 늘리는 것이 품질을 올리는 가장 싼 길이다. `PhrasebookTest` 가 열쇠 모양을
(공백·부호 없음, `ChatText.normalize` 를 통과한 모습) 못 박아 둔다.

`TargetLanguage.phrasebook` 은 ML Kit 의 `code` 와 따로 적어 둔다 — 남의 상수에 기대면
값이 바뀔 때 표가 조용히 안 맞게 된다.

**ML Kit 자체의 품질은 이걸로 못 고친다.** '저는 좋아요' → "I like it" 같은 오역은 모델 한계다.
더 좋게 하려면 서버 LLM 으로 '고급 번역' 버튼을 따로 두는 길뿐이다(AI 교정과 같은 통로).

## 도구 줄 아이콘을 그림으로 (2026-09-13)

도구 줄 동그라미는 전부 글꼴 기호였는데, 클립보드만 삼성과 모양이 달랐다. '▤'(U+25A4)는
줄 친 네모라 표에 가깝고, 진짜 클립보드 글자인 '📋'는 컬러 이모지라 단색 선 아이콘들과
톤이 어긋난다. 그래서 `res/drawable/ic_clipboard.xml` 로 직접 그렸다 — 둥근 판의 윗변
가운데가 파이고 그 자리에 집게가 얹힌 모양(삼성과 같다).

판과 집게를 **한 획**으로 잇는다. 따로 그리면 판의 윗줄이 집게를 가로질러 지나가 지저분하다.

동그라미 버튼은 `TextView` 라 그림을 넣으려면 배경을 두 겹으로 쌓는다 —
`LayerDrawable(동그라미, InsetDrawable(아이콘, 여백))`. 사방 여백이 같아 저절로 가운데
놓인다. 색은 `styleClipboardButton()` 이 테마 글자색으로 입힌다. 아이콘 크기는
`TOOLBAR_ICON_DP = 16` 으로, 옆의 글꼴 기호(18sp)들과 눈높이를 맞춘 값이다.

**이 컨테이너에서는 APK 를 못 만들어 아이콘을 볼 수 없다.** 경로가 맞는지는 스크래치패드에서
SVG 호를 점으로 펴서 ASCII 로 찍어 확인했다. 다른 아이콘을 그릴 때도 같은 방법을 쓸 것.

## APK 용량 (2026-09-13)

86MB 까지 커져서 안을 열어 봤다 (`unzip -l` 로 항목별 합계). 두 번 뛰었다.

| 커밋 | 아티팩트(zip) | 무엇이 들어왔나 |
|---|---|---|
| 1433087 이전 | 10.9MB | 형태소 사전만 |
| 35b1ba8 | 23.1MB | **어절 언어모델** `lm.bin.gz` 12MB |
| 231784b | 51.4MB | **ML Kit 번역** 네이티브 라이브러리 |

APK 안 내용(93.7MB):

| 내용물 | 크기 |
|---|---|
| lib/x86_64 | 17.4MB |
| lib/x86 | 17.3MB |
| lib/arm64-v8a | 16.4MB |
| lm.bin.gz | 12.1MB |
| lib/armeabi-v7a | 11.6MB |
| 코드(dex) | 10.0MB |
| lexicon.bin.gz | 5.5MB |

번역기가 CPU 종류마다 네이티브 라이브러리를 하나씩 들고 와서 그것만 62.7MB 다. 그중
**x86·x86_64 34.7MB 는 에뮬레이터 전용**이라 실제 폰에서는 안 쓰인다. `abiFilters` 로
뺐다 (`keyboard/build.gradle.kts`). armeabi-v7a 는 남겼다 — 오래된 보급형 폰이 쓴다.
에뮬레이터로 시험할 일이 생기면 `"x86_64"` 를 잠깐 도로 넣으면 된다.

**네이티브 라이브러리는 APK 안에서 압축되지 않는다** (AGP 4 부터 `extractNativeLibs=false`
가 기본 — mmap 으로 바로 읽으려고). 그래서 APK 파일 크기는 커 보여도 아티팩트 zip 은
51MB 고, Play 가 내려보내는 것은 기기에 맞는 ABI 하나뿐이라 더 작다.

더 줄일 여지: 코드(dex) 10MB 는 릴리스에서 `isMinifyEnabled = true` 로 줄일 수 있다.
지금은 꺼 둔 상태다 — 켜면 R8 이 ML Kit·Billing 의 리플렉션을 건드려 깨질 수 있어
실기기 확인이 필요하다.

## 서버 번역 (프리미엄) — "현지인처럼 자연스러운 번역" (2026-09-13)

기기 번역(ML Kit)은 천장이 낮다. 그 위를 구독자에게만 연다.

| | 무료 | 프리미엄 |
|---|---|---|
| 치는 동안 보이는 번역 | ML Kit, 무제한, 오프라인 | 같음 (미리보기) |
| 실제로 나가는 번역 | ML Kit | **서버 LLM** |
| 입력란 통째 번역 | 없음 | 번역 동그라미 **길게 누르기** |

### 한도는 교정과 한 통

글자당 값이 교정과 똑같아서(같은 모델, 비슷한 토큰 수) 따로 셀 이유가 없다. 구독자는
이미 글자로 세고 있으므로(`chars:<installId>`) 번역도 그 통을 쓴다. **새로 만든 한도 코드가
없다.** 앱에 안내하는 "하루 10만 자" 문구도 그대로다.

글자당 0.00156원. 30자 메시지 0.066원, 2,000자 장문 3.14원.
프리미엄 실수령 2,691원/월 기준 본전이 되는 지점은 하루 5만 7천 자다. 10만 자를 매일
꽉 쓰는 사람이 나오면 그 사람에게서는 월 2,020원 손해다. 그런 사람이 실제로 생기면
`SUB_DAILY_CHARS` 를 낮추면 된다.

**진짜 위험한 쪽은 무료다.** 받는 돈이 0인데 하루 5회 × 2,000자를 꽉 쓰면 한 명당 월 471원,
1만 명이면 471만 원이다. `FREE_DAILY_LIMIT` 이 그 선을 지킨다 — 지금 시험용 200 이니
**출시 전에 반드시 5 로 되돌릴 것.**

### 어떻게 붙였나

- 서버 `?translate=en` 쿼리 하나로 갈린다. 헤더가 아니라 주소에 싣는 이유는
  `GeminiCorrector.Transport` 가 요청마다 헤더를 못 바꾸게 되어 있어서다(고정 헤더만
  생성 때 받는다). 그 규약을 번역 하나 때문에 흔들 이유가 없고, 서버는 경로만 보고
  라우팅하므로 물음표 뒤는 그냥 통과한다.
- `translatePrompt(target)` 이 언어별 지시문을 만든다. 빠진 주어 채우기, 말투 맞추기,
  직역 금지가 핵심이다. 교정 지시문과 같은 원칙을 지킨다 — **사용자 글은 자료지 지시가 아니다.**
- `toGeminiReply` 의 길이 검사(`tooDifferent`)는 번역일 때 건너뛴다. 한국어 20자가 영어
  40자가 되는 건 정상인데, 그대로 두면 멀쩡한 번역이 전부 502 로 막힌다.
- 앱은 번역 요청에 교정 지시문을 안 싣는다(`buildRequest(text, withPrompt = false)`).
  서버가 자기 지시문을 쓰므로 2KB 를 같이 보낼 이유가 없다.
- 실패하면 기기 번역문을 그대로 보낸다. 못 보내는 것보다 낫다.

### 주의

- `TargetLanguage.tag` 가 우리 규약(관용구 표 열쇠 + 서버 언어 이름)이고 `code` 는 ML Kit
  것이다. 지금은 값이 같지만 묶지 마라 — 그쪽이 바뀌면 둘 다 조용히 안 맞게 된다.
- 도구 줄 단추는 원래 **누르는 순간** 실행한다(자판 키와 같다). 번역 단추만 길게 누르기가
  있어서 짧게 누르면 손 뗄 때 실행한다(`toolbarTouch`). 안 그러면 길게 누른 사람에게
  입력줄 열기와 입력란 번역이 둘 다 일어난다.
- 구독 여부는 앱이 서버 헤더(`x-plan`)를 기억해 둔 값으로 본다. 폰의 값은 고칠 수 있지만
  **진짜 판단은 서버가 한다** — 구독자가 아닌데 보내면 서버가 막는다. 앱의 판단은 화면을
  어떻게 보여줄지 정하는 용도다.

### 후행 람다 함정 — 빌드를 한 번 깨뜨렸다 (2026-09-13)

`toolbarButton(label, onPress)` 에 길게 누르기를 붙이면서 `onLongPress` 를 **뒤에** 달았다.

```kotlin
// 이렇게 고쳤더니
private fun toolbarButton(label: String, onPress: () -> Unit, onLongPress: (() -> Unit)? = null)
// 기존 부르는 쪽이 전부 조용히 깨졌다
emojiButton = toolbarButton("☺") { showEmoji() }   // 이 람다가 onLongPress 로 붙는다
```

아홉 군데에서 `No value passed for parameter 'onPress'`. **람다를 받는 인자는 마지막에
두어라.** 지금은 `toolbarButton(label, onLongPress = null, onPress)` 순서다.

#### 로컬 검사로는 못 잡는다

이 저장소는 안드로이드 SDK 없이 도는 환경이라, `keyboard/` 는 그래들로 못 짓고 그래들에
딸린 kotlinc 로 문법만 본다:

```
CP=$(ls /opt/gradle-8.14.3/lib/kotlin*.jar /opt/gradle-8.14.3/lib/annotations-*.jar \
       /opt/gradle-8.14.3/lib/trove4j*.jar | tr '\n' ':')
java -cp "$CP" org.jetbrains.kotlin.cli.jvm.K2JVMCompiler -nowarn -d /tmp/out \
     keyboard/src/main/java/com/spellkeyboard/ko/*.kt
```

`android.*` 가 없으니 에러가 1,700 개쯤 쏟아진다. 대부분 `unresolved reference` 와 그
뒤끝(`overrides nothing`, `no 'get' operator`, `val cannot be reassigned`)이라 **신호가
아니다**. 쓸모 있는 건 **괄호·중괄호가 안 맞는 종류**의 문법 오류뿐이다.

인자 결합 오류는 여기서 **안 나온다**. 타입이 ERROR 라 컴파일러가 결합 단계까지 가지
않는다. 실제로 그때 로그에 `No value passed for parameter` 가 0 건이었다. 그래서 글자로
보는 검사를 따로 둔다 — 기본값 없는 람다 인자가 마지막이 아닌 함수를 찾아내는 것.
`keyboard/` 를 고칠 때는 이 함정을 눈으로 한 번 더 확인해라.

## 결제 없이 유료 기능을 시험하는 길 (2026-09-13)

AI 번역은 구독자 전용인데, 구독 판단은 Play 구매 토큰을 구글에 물어보는 것뿐이었다
(`isSubscriber`). Play Console 등록 전에는 개발자 자신도 켤 방법이 없었다.

`TEST_INSTALL_IDS` **비밀값**에 설치 ID 를 쉼표로 적어 두면 그 기기만 구독자로 친다
(`isTestSubscriber`, `server/src/index.js`).

- 값은 코드에도 `wrangler.toml` 에도 없다. GitHub 비밀값 → 배포 일감이
  `wrangler secret put` 으로 넣는다. 저장소가 공개라 이 경로 말고는 두지 않는다.
- 설치 ID 는 앱이 처음 켜질 때 만든 UUID 다. 남이 맞힐 수 없고, 새더라도 잃는 것은
  그 기기 하나의 무료 한도뿐이다.
- 설정 화면 맨 아래에 설치 ID 를 보여 준다(`install_id`, 길게 눌러 복사).

### 출시 전에 지울 것

1. GitHub 비밀값 `TEST_INSTALL_IDS` 삭제
2. `cd server && npx wrangler secret delete TEST_INSTALL_IDS`

무료 AI 를 닫은 뒤로 이것이 **유일한** 출시 전 되돌리기 항목이다.

### 알아 둘 것 — 요금제는 AI 를 한 번 써야 알게 된다

앱은 서버가 헤더(`x-plan`)로 알려 준 값을 기억해서 구독 여부를 본다(`noteQuota`).
설치 직후에는 그 값이 없어서 **AI 교정을 한 번 눌러야** 구독자로 인식하고, 그 뒤부터
번역 보내기가 서버 번역을 탄다. 이것은 버그가 아니라 "판단은 서버가 한다" 는 설계의
결과다 — 폰이 스스로 구독자라고 우기지 못하게 하려고 이렇게 뒀다.

## 무료에서 AI 를 아예 뺐다 (2026-09-13)

무료 요금제에 AI 를 남겨 두면 **쓰는 사람이 늘수록 손해가 는다.** 무료 한 명이 하루
한도를 꽉 채우면 월 468원이 나가고 받는 돈은 0원이다. 100만 명이면 월 4.7억이다.
한도를 낮춰도 방향은 그대로고, 서버 주소는 APK 안에 있어 누구나 두드릴 수 있다.
확실한 천장은 "돈 낸 사람만" 하나뿐이다.

### 무엇이 어떻게 바뀌었나

| | 전 | 후 |
|---|---|---|
| 무료 AI 교정 | 하루 5회 | **없음** (402 `subscribers_only`) |
| 무료 AI 번역 | 없음 | 없음 |
| 실시간 온디바이스 교정 | 무제한 | **무제한** (그대로) |
| 기기 번역(ML Kit) | 무제한 | **무제한** (그대로) |
| 프리미엄 | 하루 10만 자 | 하루 10만 자 (그대로) |

무료 사용자가 잃는 것은 서버 기능뿐이다. 키보드로서 하는 일 — 실시간 맞춤법·띄어쓰기
교정, 천지인, 배경 사진, 기기 번역 — 은 전부 그대로다. 안내 문구도 "다 썼다" 가 아니라
"프리미엄 기능이고 실시간 교정은 늘 무제한" 으로 적는다.

### 지운 것

- `FREE_DAILY_LIMIT`, `IP_DAILY_LIMIT` (wrangler.toml)
- `decide()` 호출, `ipBucket()`, `bump()` (index.js) — 무료 경로가 사라지면서 죽은 코드
- IP 한도 시험 — 무료가 LLM 에 닿지 못하니 막을 것이 없다

설치 ID 를 갈아 끼우며 두드리는 공격은 **전보다 싸졌다**. 예전에는 무료 5회씩 진짜
요청이 나갔지만, 이제는 402 를 즉시 돌려주고 LLM 까지 가지 않는다.

### 창을 넓혔다 (같이 한 것)

무료를 닫고 나니 보내는 글자를 아낄 이유가 사라졌다. AI 를 쓰는 사람은 전부 구독자고,
천장은 앱이 아니라 서버의 하루 글자 수다.

| | 전 | 후 | 왜 |
|---|---|---|---|
| `AI_BEFORE_CHARS` | 1,500 | 4,000 | 긴 글이 조용히 반만 고쳐지면 고장으로 보인다 |
| `AI_AFTER_CHARS` | 500 | 2,000 | 〃 |
| `AI_WATCHDOG_MS` | 35초 | 60초 | 글이 길수록 모델이 쓰는 시간도 길다 |
| `READ_TIMEOUT_MS` | 15초 | 40초 | **이게 진짜 병목이었다** — 답이 오는 중에 우리가 끊었다 |

창 하나가 6,000 자라 하루 10만 자면 꽉 채운 교정 16번이다. 실제로는 카톡 몇 줄이
대부분이라 훨씬 많이 쓴다.

### CI 연기 시험이 잃은 것 (알아 둘 것)

배포 일감 끝의 "교정 한 번" 은 `ci-smoke-test-0000` 이라는 설치 ID 로 보낸다. 무료를
닫은 지금 이건 **402 가 정상**이고, 그래서 이 단계는 "서버가 살아 있고 무료를 제대로
막는다" 까지만 증명한다. OPENAI_API_KEY 가 망가져도 배포는 초록으로 보인다.

여기에 구독자 설치 ID 를 박을 수는 없다 — 공개 저장소라 그걸 쓰는 사람 누구나 공짜로
AI 를 쓰게 된다. LLM 이 진짜 답하는지는 구독자 기기에서 한 번 눌러 보는 것으로 본다.

반대로 저 자리에 **200 이 찍히면 이상한 것이다** — 무료가 뚫렸다는 뜻이다.

## "제미나이 때보다 못하다" — 되돌린 것 (2026-09-13)

실기기 평가: **정확도가 떨어지고 속도도 느리다. 기본적인 맞춤법도 자꾸 틀린다.**
짚어 보니 셋 다 우리가 스스로 만든 것이었다.

### 1. 숙고를 다시 깎아 놨다 (정확도)

품질 보정 1차에서 Gemini 와 벌어진 원인 셋 중 하나로 **`minimal`** 을 지목하고
`low` 로 올렸었다. 그런데 나중에 "교정 한 번에 7초" 를 줄이려고 **도로 `minimal` 로
내렸다.** 그때 적어 둔 조건 — "품질이 떨어지면 low 로 되돌린다" — 이 실현된 것이다.

`low` 로 되돌렸다. 속도는 아래 2번에서 벌어 온다.

### 2. 가장 먼 미국을 골라 놨다 (속도)

바깥 호출은 미국에 붙박이인 Durable Object 안에서 한다. 한국 트래픽이 홍콩 센터에
붙으면 구글·OpenAI 가 "User location is not supported" 로 거절하기 때문이다. 이 이유는
지금도 유효하다. 문제는 **어느 미국이냐**였다.

`enam`(미국 동부)은 서울에서 가장 먼 축이다. 요청은 태평양을 두 번 건넌다:
폰 → 서울 엣지 → 이 객체 → 모델 → 되돌아오기. `wnam`(미국 서부)으로 옮긴다.
홍콩 문제는 그대로 피하면서 왕복이 눈에 띄게 짧아진다.

**함정**: 위치 힌트는 **객체를 처음 만들 때만** 먹는다. `RELAY_LOCATION` 만 고치면
이미 동부에 만들어진 객체를 계속 쓰고 **아무 일도 안 일어난다.** 그래서 이름도 같이
바꿨다(`google-relay` → `relay-wnam`). 이 객체는 저장하는 것이 없어서 버려도 된다.
시험이 이 짝을 지킨다.

### 3. 아직 안 건드린 것 — 모델

`gpt-5-mini` 다. 9/12 에 이미 "예전 Gemini 는 100%, gpt-5-nano 는 95%" 라는 평가가
있었고, 그 뒤로 지시문과 모델 등급으로 메워 왔지 **Gemini 수준으로 되돌린 적은 없다.**

되돌리는 길 자체는 열려 있다 — `OPENAI_API_KEY` 비밀값 하나를 지우면 서버는 다시
구글로 간다(`openAiModel()`). `GEMINI_API_KEY` 도 아직 들어 있다.

**다만 그냥 지우면 번역이 깨진다.** 번역 지시문은 OpenAI 쪽(`askOpenAi`)에만 붙어
있고, 구글 경로(`relay`)는 앱이 보낸 본문을 그대로 넘길 뿐이다. 구글로 돌아가려면
번역 지시문을 그 경로에도 붙여야 한다. 교정만 보면 예전 그대로 동작한다.

1·2 를 먼저 내보내고 실기기에서 다시 재 본 뒤에 정한다.

## 제미나이로 되돌리고 한도를 2만 자로 (2026-09-13)

### 제미나이로 되돌렸다

`AI_PROVIDER = "gemini"` 한 줄이다. 이유 셋이 전부 모델을 바꾸면 사라진다:

1. **`temperature: 0` 이 되살아난다.** 앱은 원래 이걸 보내는데 gpt-5 계열은 이 항목을
   받으면 400 이라 서버가 빼고 보냈다. 그래서 같은 글을 두 번 고치면 답이 달랐다.
   품질 보정 1차에서 **Gemini 와 벌어진 원인 1번**으로 지목했던 것이 이거다.
2. **숙고 대기가 사라진다.** "교정 한 번에 7초" 의 정체가 이것이었다 — gpt-5 는 답보다
   숙고를 먼저 뱉고, 그 시간이 고스란히 대기 시간이다.
3. 사용자가 100% 라고 평가한 모델이 이쪽이다.

#### 비밀값이 아니라 설정으로 갈리게 했다

예전에는 `OPENAI_API_KEY` **존재**로 갈렸다. 그러면 구글로 되돌리려고 멀쩡한 키를
지워야 하는데, 배포 일감은 비밀값을 지우지 않으므로(되묻기라 CI 에서 조용히 실패한다)
사람이 손으로 wrangler 를 쳐야 하고 되돌릴 때 키를 다시 붙여넣어야 한다.
**어느 모델을 쓰느냐는 설정이지 비밀이 아니다.** `AI_PROVIDER` 로 갈린다.
안 적으면 예전 규칙 그대로다.

#### 구글 경로를 제대로 만들었다 (`src/gemini.js`)

예전 구글 경로는 받은 것을 그대로 넘기는 통로였다. 그래서 OpenAI 쪽에만 있던
안전장치 둘이 없었다. 앱은 받은 글로 입력란을 **통째로 덮으므로** 이게 없으면:

- 잘린 답(`MAX_TOKENS`)을 받으면 **사용자가 쓴 글이 그만큼 사라진다**
- 교정이 아닌 답(요약, 본문 속 지시문 따라가기)이 그대로 입력란에 들어간다

둘 다 붙였다. 프롬프트 주입의 마지막 방어선이기도 하다.

**교정은 앱 본문을 그대로 넘긴다.** 되돌리려는 것이 "제미나이 시절" 이고 그 시절
교정은 앱 지시문으로 돌았다. 서버 지시문(`KO_SYSTEM_PROMPT`)은 작은 OpenAI 모델이
글자를 지어내는 것을 막으려고 쓴 것이라, 여기에 끼얹으면 되돌리는 게 아니라 또 다른
조합이 된다. 번역만 우리 지시문을 쓴다 — 앱이 번역 지시문을 아예 안 보내기 때문이다.

모델 목록(`/v1beta/models`)도 이제 **밖에 묻지 않는다.** 어느 쪽이든 서버가 모델을
정하므로 물어볼 것이 없다. 앱이 맨 처음 하는 일이라 이 한 번이 그대로 첫 교정의
대기 시간이었다.

### 한도를 10만 → 2만 자로

10만 자는 A4 25 장이라 **아무도 못 닿는 천장**이었다. 닿지 않는 천장은 광고 문구일
뿐 요금을 막아 주지 않는다. 제미나이는 글자당 값이 더 비싸서 그 천장이 실제로 위험해진다.

2만 자면 카톡 한 줄(30자) 660번, 긴 문자(500자) 40번이다. 실제 사용(하루 5천 자)의
네 배라 평범한 사용자는 여전히 못 닿는다.

| 한 사람이 매일 꽉 채웠을 때 | 원가/월 | 이익 |
|---|---|---|
| 500자 × 40번 | 2,852원 | −310원 |
| 50자 × 400번 (가장 나쁜 경우) | 4,025원 | −1,483원 |
| **흔한 경우 (하루 5천 자)** | **713원** | **+1,829원** |

10만 자 시절의 가장 나쁜 경우가 월 14,259원이었으니 천장이 3.5분의 1 이 됐다.

### 구글도 캐싱이 자동이다 (앞서 적은 것 정정)

"구글은 캐싱이 자동이 아니라 따로 붙여야 한다" 고 적었는데 **틀렸다.** 구글도 암묵
캐싱(implicit caching)이 기본으로 켜져 있고 90% 깎아 준다. Gemini 2.5 이상이면 자동이고
우리 모델은 3.5 라 해당된다. **코드로 붙일 것이 없다.**

짧은 호출에서 이게 크다 — 300자 호출이면 지시문 토큰이 본문의 7.4배라, 요금 대부분이
"고칠 글" 이 아니라 "매번 딸려가는 지시문" 이다.

### 창과 한도는 같이 정해야 한다 (되돌림)

교정 창을 6,000 자(4000+2000)로 넓힌 적이 있다. 하루 한도가 10 만 자일 때는 꽉 채운
교정 16 번이라 말이 됐는데, 한도를 2 만 자로 내리면서 **같은 창이 하루 세 번**이 됐다.
두 값을 따로 건드린 탓이다. 제미나이 시절 값(1500+500)으로 되돌렸다 — 하루 10 번이고,
카톡 한 줄은 최소 과금 50 자라 400 번이다.

**창을 바꾸면 `SUB_DAILY_CHARS` 를 같이 보고, 한도를 바꾸면 창을 같이 봐라.**

### 무엇이 발목을 잡고 있었나 — 절제 실험

품질이 안 오른 이유는 점수가 나빠서가 아니라 **정답이 후보에 오르지도 못해서**였다.
'시간이걸린다'를 재 보면 정답('시간이 걸린다')이 −13.61 로 우리 답('시간이걸 린다',
−32.56)보다 19점이나 좋은데도 안 나왔다.

범인은 `boundaryCost` 의 금지 조항들이었다. 하나씩 꺼 보고 쟀다.

| 껐을 때 | 오교정 | 띄어쓰기 | 망침 |
|---|---|---|---|
| (원래) | 0.27% | 64.8% | 46 |
| `isWellFormed` 금지 | 0.27% | 66.1% | 43 |
| + 바이그램 요구 | 0.27% | 66.6% | **34** |

| + 매인 형태소 금지 | 0.40% | 69.4% | 51 |

읽는 법:
- **`isWellFormed` 금지가 가장 컸다.** mecab 은 거의 모든 한글 덩어리를 어떻게든
  분석해 낸다 — '당신의선' 도 당신+의+선 으로 읽는다. "분석된다" 를 금지 조건으로

  (한 낱말 중앙값 −1331, 붙여 쓴 구 중앙값 7121 — 잘 갈린다).
- **바이그램 요구는 순손해였다.** 오교정을 전혀 줄이지 않으면서 망침만 늘렸다.

  뜻은 아니다. 뺐다.
- **매인 형태소 금지는 순이득이었다.** 재현율을 하나도 안 깎고 오교정만 줄인다. 남겼다.
- 명사|명사는 재현율을 2.8%p 깎지만 정밀도도 사 준다. 금지 대신 값(`NOUN_JUNCTION_COST`)

### 새로 넣은 신호와 규칙

- **조사·관형사·관형형 어미 뒤는 어절 경계다**(`BOUNDARY_MARKER_BONUS`).
  '컴퓨터의|충돌', '그|권리는', '읽어야 할|책들은'. 관형사(MM)를 넣은 것이 중요하다 —
  `isNominalTag` 가 MM 을 체언으로 쳐서 '그|권리는' 이 명사|명사로 **오해받고 있었다.**
- 규칙 셋(`SpacingRules`): 문장 부호 뒤 공백('네,저는'), 수관형사+단위 의존명사
  ('네개야'→'네 개야'), 보조용언('알고있다'→'알고 있다'). 이 셋만으로 68.1 → 71.0%.
  규칙은 통계가 구조적으로 못 닿는 자리를 메운다.

### 조정할 때

값을 흔들면 **반드시 세 숫자를 같이 봐라**(오교정·복원·망침). 하나만 보고 올리면
나머지가 조용히 나빠진다. 실제로 `BOUNDARY_MARKER_BONUS` 를 8 로 올리면 복원은
그대로인데 망침이 40 → 68 로 뛴다.


### 자판 위 '전체' 단추

| | 하는 일 | 요금 |
|---|---|---|
| **짧게 누르기** | 기기 안에서 글 전체 교정 | 공짜, 무제한, 인터넷 불필요 |
| 길게 누르기 | 서버 AI 로 교정 | 프리미엄, 하루 2만 자 |

자주 쓰는 쪽이 짧은 누르기다. 글자를 'AI' 가 아니라 **'전체'** 로 둔 이유는 짧게 누르는
쪽이 AI 가 아니기 때문이다. 옆의 '교정' 은 실시간 교정 켬/끔이라 이름이 겹치지 않는다.

단추 보이기 조건이 바뀌었다. 예전에는 **서버가 있을 때만** 보였는데(`setAiAvailable`),
이제 짧게 누르는 쪽이 서버와 무관하다. 대신 **고쳐도 되는 입력란인지**는 그대로
따진다(`setCorrectAllAvailable`) — 비밀번호 칸에서는 기기 안에서 도는 일이라도
교정하지 않는다. 비밀번호를 고쳐 주는 것은 도움이 아니라 사고다.

기기 안 교정은 읽는 길이도 다르다. 서버로 보낼 때는 글자가 곧 요금이라 앞 1,500 / 뒤 500
자였지만, 여기서는 아낄 이유가 없어 입력란에 있는 만큼 다 읽는다(`FULL_BEFORE_CHARS`).

## 3세대 — "도데체도 못 고치냐" 를 받고 (2026-09-13)

실기기 평가: **'도데체'도 못 고치고 '아버지가방에'도 못 띄운다. 카톡만도 못하다.**
맞는 지적이었다. 사람이 실제로 틀리는 스무 가지로 시험을 만들어 보니 15/20 이었다.

| | 전 | 후 |
|---|---|---|
| **실사용 시험** | 15/20 | **20/20** |
| 띄어쓰기 복원 | 72.4% | **73.7%** |
| **ㅐ/ㅔ 복원** | 72.2% | **78.8%** |
| 오교정 | 0.30% | 0.37% |

오교정 11건을 하나씩 읽으면 **2건은 우리가 제대로 고친 것**을 평가 원문이 틀린 채로
갖고 있어 오답으로 센 것이고('비지니스'→'비즈니스', '낫다면'→'났다면'), 5건은 둘 다
맞는 합성어 띄어쓰기다('웹사이트'/'웹 사이트'). 실제 오교정은 3건, **0.10%** 다.

### '도데체' — 사전에 없었을 뿐

이미 114개짜리 표기 사전이 있었는데 '도데체' 가 없었다. 표를 키우는 것이 정답이다 —
부산대·한컴이 하는 것이 그것이다. 160여 개를 더 넣었다(ㅐ/ㅔ 혼동, 받침·어간,
낱말 혼동, 외래어 표기, '을려고→으려고' 계열).

**표가 커지면 방식을 바꿔야 한다.** `TextRule.literal` 을 수백 개 늘어놓으면 어절마다
수백 번을 훑고, 실시간 입력 경로라 그게 그대로 타이핑 지연이 된다.
[TextRule.dictionary] 는 표 전체를 정규식 하나로 묶어 **한 번만** 훑는다.
긴 항목이 먼저 잡히게 길이 내림차순으로 놓는다 — 안 그러면 '오랫만' 이 '오랫' 에서 잘린다.

### '아버지가방에' — 모르는 말이 아는 말 둘을 이겼다

점수를 까 보니 규칙 문제가 아니라 **모델 문제**였다.

```
아버지가방에   (모르는 말 하나)  -19.08
아버지가 + 방에 (아는 말 둘)     -20.17   ← 더 나쁘다
```

원인은 또 `isWellFormed` 였다. mecab 이 '아버지가방에' 를 아버지+가방+에 로 멀쩡히
읽으니 "그냥 드문 낱말" 로 보고 길이 벌점을 거의 안 줬다(`WELL_FORMED_PER_SYLLABLE`
0.5). 모르는 6음절 어절은 그럴 리가 없다 — 2.5 로 올렸다. 이것만으로 **ㅐ/ㅔ 복원이
72 → 79%** 로 뛰었다. 모르는(= 틀리게 쓴) 낱말이 제값에 깎이기 시작해서다.

그래도 0.4점이 모자랐다. 여기서 형태소 비용은 더 못 쓴다 —
**'국민청원'(1720)과 '아버지가방에'(1733)가 거의 같다.** 가르는 것은 다른 증거다:
말뭉치에 **있었느냐**. 아는 어절은 한 낱말이라는 증거가 둘(분석 + 실제 쓰임)이고
모르는 어절은 하나뿐이다. 모르는 말은 덜 지킨다(`UNSEEN_WELL_FORMED_FACTOR`).

### 조사·어미를 떼어 내던 것

위를 풀자 새 오교정이 한 종류로 몰렸다 — '데이터로|부터의', '연루되었을|지도',
'겁먹는|다는'. 조사·어미를 어절로 떼어 낸 것이다. 분석기에 물어보는 `startsBound` 가
있는데도 새는 이유는 mecab 이 '부터'·'지도' 를 명사로도 읽기 때문이다.

표(`BOUND_STARTS`)로 받쳤다. **금지가 아니라 값이다** — '지도'(map)처럼 진짜 낱말과
겹치는 것이 있어서 증거가 확실하면 넘어갈 수 있어야 한다. 오교정 0.50 → 0.37%,
띄어쓰기는 오히려 올랐다. 순이득이다.

### 되풀이되는 교훈

이 파일에서 세 번 같은 범인이 나왔다. **`isWellFormed` 하나로 무엇을 막지 마라.**
mecab 은 거의 모든 한글 덩어리를 어떻게든 분석해 낸다 — '당신의선' 도, '아버지가방에' 도.
"분석된다" 는 약한 증거다. 값으로 쓰고, 다른 증거(말뭉치 빈도, 분석 비용)와 같이 봐라.

## 공백을 아예 안 친 글 — 평가가 놓치고 있던 진짜 쓰임 (2026-09-13)

실기기에서 띄어쓰기를 통째로 생략한 글에 전체교정을 눌렀더니 **공백이 하나도 안
들어갔다.** "1곳을 고쳤어요" 만 떴다.

원인은 쟀던 것이 잘못됐다는 데 있다. `EvaluationTest` 는 멀쩡한 문장에서 공백을
**하나만** 지우고 되돌리는지 본다. 그 숫자(73.7%)는 진짜지만, 사람이 빨리 치느라
**아예 안 띄운 글**은 완전히 다른 문제다. 그쪽은 0% 였는데 보이지 않았다.

### 막고 있던 것 둘

1. **문맥 교정기는 14음절 넘는 어절을 쳐다보지도 않는다**
   (`ContextCorrector.MAX_TOKEN_SYLLABLES`). 안 띄운 글은 30~50음절로 온다.
   `tokenize` 가 그런 조각을 soft 로 치지 않아서 `explain` 이 아예
   "고칠 수 있는 어절이 없다" 를 뱉는다.
2. **형태소 사전은 24음절까지만 본다**(`Spacer.MAX_SYLLABLES`). 그 위는 null 이다.

그런데 **형태소 사전은 24음절 안에서는 아주 잘 푼다.**
'하긴남의말을개똥으로아는놈이니오죽하겠냐마는'(22음절)을
'하긴 남의 말을 개똥으로 아는 놈이니 오죽하겠냐마는' 으로 거의 완벽하게 낸다.
좋은 도구를 안 쓰고 있었던 것이다.

### 고친 것

- `Spacer.spaceLong` — 창을 앞에서부터 밀며 푼다. **창 끝에 걸친 조각은 잘렸을 수
  있으니 내보내지 않고 다음 창으로 넘긴다.** 창이 안 나뉘면 줄여 가며 다시 본다.
  반드시 두 조각 이상을 얻어야 창이 밀린다 — 한 조각이면 제자리걸음이다.
- `CorrectionEngine.applyLongSplit` — 디코더가 못 보는 긴 덩어리를 사전이 먼저 푼다.
  그 결과를 디코더가 받아 다듬는다(과하게 나눈 자리는 KIND_MERGE 가 도로 붙인다).
- **끝의 문장 부호를 떼고 넘긴다.** 사전은 어절을 받는데 '…없더라고.' 를 통째로
  넘기면 분석이 실패한다. 이것 때문에 **마지막 조각이 늘 안 풀렸다** — 문장 끝이라
  부호가 거의 항상 붙어 있다.

| 실기기에서 받은 줄 | 전 | 후 |
|---|---|---|
| 31음절 | 공백 0 | 공백 9 |
| 32음절 | 0 | 9 |
| 40음절 | 0 | 10 |
| 46음절 | 0 | 14 |
| 31음절 | 0 | 10 |

`NoSpaceTest` 가 바닥을 못 박는다. 다른 숫자(오교정 0.37%, 띄어쓰기 73.7%,
ㅐ/ㅔ 78.8%)는 그대로고 속도도 그대로다(전체교정 2,600자 9ms).

### 교훈

**무엇을 재는지가 무엇을 고칠지를 정한다.** 공백 하나만 지운 문장으로 재는 동안
진짜 쓰임은 0% 인 채로 세 판이 지나갔다. 새 기능을 만들면 **그 기능이 실제로 받게
될 입력**으로 재라.

## 꾹 눌러도 AI 가 안 되던 것

도구 줄 단추의 `insideView` 가 뷰 경계를 **딱 맞게** 봤다. 길게 누르는 동안 손가락이
1픽셀만 흔들려도 밖으로 나간 것이 되어 `cancel()` 이 돌고, 길게 누르기도 짧게
누르기도 죽는다. 동그라미가 28dp 라 더 그렇다.

안드로이드 터치 슬롭의 3배를 여유로 둔다(`TOUCH_SLOP_FACTOR`). 사람 손가락은
가만히 있어도 떨린다 — 슬롭이 있는 이유가 그거다.

## Kiwi 를 붙이기로 한 근거 (2026-09-13)

"부산대 같은 좋은 엔진 못 얻어오냐" 는 물음에 [Kiwi](https://github.com/bab2min/Kiwi)를
실제로 받아서 재 봤다. 결론부터: **공백 없는 글에서는 Kiwi 가 확실히 이긴다.**

### 받을 수 있는 것 (v0.23.2)

| | |
|---|---|
| 안드로이드 AAR | 10.5MB — `jni/arm64-v8a/libKiwiJava.so`(9.9MB) + x86_64(16.7MB) |
| **armeabi-v7a** | **없다.** 32비트 폰은 기존 엔진으로 남아야 한다 |
| 모델 | 84MB 압축 / 105MB 해제 |
| `cong.mdl`(72MB) 빼기 | **안 된다.** 없으면 "Cannot find any valid model files" |
| `ModelType.knlm` | 이 꾸러미에 `sj.knlm` 이 없어 못 쓴다 |
| 모델 올리는 시간 | **약 5초** (한 번) |
| 라이선스 | v0.23.2 는 LGPL (Apache 2.0 은 아직 미출시) |
| `space()` | **자바 바인딩엔 없다.** kiwipiepy 쪽에만 있어 직접 만들어야 한다 |

### 잰 것 — 자를 두 개 써야 답이 갈린다

**멀쩡한 문장**(공백 하나만 지운 것)으로 재면 Kiwi 가 진다.

| | 우리 | Kiwi(태그) | Kiwi(조사·어미 뒤에만) |
|---|---|---|---|
| 오교정 | **0.37%** | 18.47% | 6.90% |
| 띄어쓰기 복원 | **73.7%** | 78.8% | 72.5% |

**공백을 전부 지운 문장**(전체교정이 실제로 받는 것)으로 재면 뒤집힌다.

| | 우리 | **Kiwi(태그)** |
|---|---|---|
| 정밀도 | 92.2% | **95.6%** |
| 재현율 | 83.4% | **96.7%** |
| **F1** | 87.6% | **96.1%** |
| 문장 통째로 | 44.2% | **66.2%** |

같은 엔진이 자에 따라 이기고 진다. **"어떤 입력을 받느냐" 를 먼저 정해야 엔진을 고를 수
있다.** 멀쩡한 글에 Kiwi 를 들이대면 멀쩡한 띄어쓰기를 헤집는다 —
멀쩡한 띄어쓰기가 없는 덩어리에는 그 위험이 없다.

### 그래서 붙이는 방식

**공백 없는 긴 덩어리에만 Kiwi 를 쓴다.** 나머지(실시간 교정, 공백이 있는 글)는 우리
엔진 그대로다. 이기는 자리에만 쓰고, 지는 자리에는 안 쓴다.

`BareTextTest` 가 우리 쪽 숫자를 지킨다(`SPELL_EVAL_FILES` 가 있을 때만 돈다).

### 붙인 방식

| 어디 | 무엇 |
|---|---|
| `keyboard/build.gradle.kts` | `fetchKiwi` 가 빌드할 때 AAR·모델을 받는다. **저장소에 안 넣는다** — 남의 산출물 94MB 를 git 에 넣으면 clone 이 그만큼 무거워진다 |
| `core/…/spacing/LongSpacer.kt` | 코어에는 **자리만** 둔다. 코어는 안드로이드에도 Kiwi 에도 기대지 않는다 |
| `keyboard/…/KiwiSpacer.kt` | 실제 구현. 에셋의 모델을 파일로 꺼내고(네이티브가 mmap 해야 한다) Kiwi 를 올린다 |
| `CorrectionEngine.applyLongSplit` | `longSpacer` 가 있으면 그쪽, 없으면 기존 `Spacer.spaceLong` |

**없을 수 있다는 것이 설계의 일부다.** Kiwi 네이티브 라이브러리는 arm64-v8a 에만 있어서
32비트 폰에서는 안 올라온다. 모델을 못 꺼낼 수도, 메모리가 모자랄 수도 있다.
그때 `KiwiSpacer.open` 이 null 을 주고 **기존 엔진이 그대로 그 일을 한다.**
이 기능이 없다고 교정이 멈추면 안 된다.

올리는 순서도 중요하다. 형태소 사전 → 언어모델 → Kiwi 순이다. Kiwi 는 105MB 를 꺼내고
읽느라 수 초가 걸려서, 앞의 둘이 먼저 준비돼야 그 동안에도 교정이 된다.

**토큰 표면을 이어 붙이면 안 된다.** 축약형('했' = 하 + 았)은 여러 형태소가 같은 자리를
가리켜서 글자가 겹친다('말했했잖아'). 원문은 그대로 두고 **공백만 끼워 넣는다.**

### 규칙 다듬기 — 통째 66.2% → 68.7%

Kiwi 를 붙인 뒤 실기기에서 "같은 문장 오타가 8개에서 4개로 줄었다" 는 평가가 왔다.
남은 것을 보고 두 가지를 고쳤다.

| 고친 것 | 통째 |
|---|---|
| 그대로 | 66.2% |
| **+ `vcn`**(부정지정사 '아니다') | 67.6% |
| **+ '-어지다' 붙임** | **68.7%** |

- **`vcn` 이 빠져 있었다.** '게아니라고'·'거아니냐' 가 안 띄워진 이유다.
- **'-어지다' 는 앞말에 붙여 쓴다**('행복해지는', '이어지는'). Kiwi 는 이걸 떼어 놓아서
  '행복해 지는' 이 됐다. 말뭉치를 세어 보니 붙여 쓴 것 뿐이고 띄어 쓴 예가 **0** 이다.

**'하' 는 넣지 않았다.** 같은 보조용언이라도 '해야 하는' 은 띄어 쓴다. 같이 넣었더니
통째가 67.6% → **65.1%** 로 내려갔다 — '차려야하는' 이 돼서다. 규칙을 넓힐 때는
반드시 재라, 비슷해 보이는 것이 반대로 움직인다.

### 합성어 — Kiwi 한테 한 번 더 물어보면 된다

'개똥으로' 가 '개 똥으로' 가 됐다. 이유는 규칙 그 자체다. "내용어 태그 앞에서 띄운다"
인데 합성어는 **내용어가 둘 연달아** 오는 것이라 무조건 갈라진다 — 문장 속에서 Kiwi 는
'개똥' 을 개/NNG + 똥/NNG 로 본다.

"명사+명사는 안 쪼갠다" 는 뭉툭한 규칙을 먼저 대 봤는데 정밀도는 올랐지만(95.6 →
97.5%) 재현율이 무너졌다(97.0 → 88.4%, 통째 67.6 → 49.6%). 세상의 명사+명사가 다
합성어는 아니다.

**되는 방법은 Kiwi 한테 따로 물어보는 것이다.** 붙인 것만 떼어서 혼자 돌려 보면:

| 붙인 것 | 혼자 돌렸을 때 | 판정 |
|---|---|---|
| 개똥 | `개똥/NNP` — 형태소 하나 | 한 낱말, 붙인다 |
| 일처리 | `일/NNG + 처리/NNG` | 두 낱말, 띄운다 |
| 봄바람·길거리·밥상·소고기 | 하나 | 붙인다 |
| 이번주말·학교종·상금중 | 둘 | 띄운다 |

문장 전체를 볼 때는 문맥 확률이 끼어들어 합성어가 갈라지는데, 그 두 글자만 주면
사전이 아는 대로 답한다. 이 답을 그대로 쓴다(`KiwiSpacer.isOneWord`).

| | 정밀도 | 재현율 | F1 | 통째 |
|---|---|---|---|---|
| 전 | 95.9 | 96.9 | 96.4 | 68.7% |
| 후 | **96.3** | 96.8 | **96.5** | **69.3%** |

정밀도만 오르고 재현율은 그대로다 — 뭉툭한 규칙과 정확히 반대다. 전체 경로로도
통째 66.5 → **66.9%**, 형이 준 다섯 줄은 **다섯 줄 다** 맞는다.

경계마다 `tokenize` 를 한 번 더 부르지만 명사가 둘 붙은 자리에서만이고 답을 기억해
둔다. 3,000 문장에 0.2초 더 걸렸다.

### 남은 것 하나

1. **우리 후처리가 Kiwi 결과를 조금 깎는다** — Kiwi 만 68.7%, 전체 경로는 66.5%.
   우리 규칙·디코더가 Kiwi 가 맞게 띄운 자리를 되돌리는 것이 있다. 어느 쪽인지
   (`applyContext` 인지 `applyTextRules` 인지) 아직 안 갈라 봤다. 다음에 볼 것.

### 시험이 디스크를 채우고 있었다 (같이 고침)

`SpacingDictionary.open`·`LanguageModel.open` 은 받은 폴더에 자원을 **푼다**(언어모델만
62MB). 시험마다 `createTempDirectory` 를 부르고 있어서 그 62MB 가 시험 수만큼 쌓였다 —
한 세션에 **358개, 18GB** 가 남아 빌드가 "No space left on device" 로 죽었다.

`deleteOnExit` 는 도움이 안 된다. **빈 폴더만** 지우고, 그것도 JVM 이 곱게 끝날 때만이다.

`TestCache.dir` 하나를 같이 쓴다. 임시 폴더 밑의 **고정된 이름**이라 쌓이지 않고,
이미 풀려 있으면 다시 쓴다 — 푸는 일이 한 번이라 시험도 빨라진다.

## '고칠 것이 없습니다' 가 거짓말이던 것

실기기에서 여섯 줄짜리 글에 '전체' 를 눌렀더니 **"AI 가 보기에 고칠 것이 없습니다"**
가 떴다. 그 글에는 '어그저께' 가 있었다.

두 가지가 겹쳐 있었다.

**하나, 말이 틀렸다.** `ai_unchanged` 문구를 기기 안 교정(짧게 누르기)과 서버
AI(길게 누르기)가 **같이** 쓰고 있었다. 짧게 눌렀는데 "AI 가 보기에" 라고 나오니,
쓰는 사람은 서버까지 갔다 온 줄 알고 AI 를 다시 안 눌러 본다. 기기 안 교정은 이제
`correct_all_unchanged` — "고칠 것을 못 찾았어요. 꾹 누르면 AI 가 봅니다" 다.
**두 경로가 같은 말을 하면 어느 쪽이 돌았는지 알 수 없다.**

**둘, 정말로 못 고쳤다.** '어그저께' 가 표에 없었다. '어제그저께' 의 준말이라
'어제' 의 'ㅔ' 가 줄고 'ㅈ' 만 앞 음절 받침으로 남는다(한글 맞춤법 32항) — '엊그저께'.
'어그저께/엇그저께/어그제/엇그제' 를 넣었고, 같이 비어 있던 스물여섯을 채웠다
(빈털털이·사겼·어느세·낭떨어지·부딧·숫가락·쑥쓰·가르키·귀뜸·괜시리·느즈막·뭉기적·
아지랭이·쭈꾸미·칠흙·쉽상·우유곽·쑥맥·허구언·어따대고·숨박꼭질·일사분란·풍지박산·
동거동락·환골탈퇴).

**넣기 전에 말뭉치로 확인한 것**: 이 스물여섯 중 어느 것도 XNLI 4만 문장에 **한 번도**
안 나온다. 즉 멀쩡한 글을 건드릴 일이 없다. 표가 부분 문자열로 걸리기 때문에 이
확인이 꼭 필요하다 — '구지 → 굳이' 를 표에 넣으면 **'대구지역'** 이 '대굳이역' 이 된다
(그래서 그건 `^구지$` 규칙으로 따로 있다). '임마 → 인마' 도 '임마누엘' 때문에 못 넣는다.

그 글에서 안 고친 나머지는 일부러 둔 것이다. '그제서야' 는 예전엔 비표준이었지만
'이제서야' 가 표준형이 되면서 같이 인정하는 쪽으로 갔다 — 논란 중인 것은 안 건드린다.
'밥 한 번' 도 횟수로 읽으면 맞아서 그대로 둔다.

## 그레이들 없이 :core:test 돌리기

이 컨테이너의 망 정책이 **`dl.google.com` 을 막는다**(프록시가 CONNECT 에 403).
안드로이드 그레이들 플러그인을 거기서 받아야 해서 `./gradlew :core:test` 도 죽는다 —
루트 `build.gradle.kts` 가 `apply false` 로라도 그 플러그인을 걸어 두기 때문이다.
그레이들 캐시가 살아 있을 때만 됐던 것이고, 캐시를 지우면 못 돌린다.

core 는 순수 코틀린이고 의존성이 stdlib 하나뿐이라 직접 돌릴 수 있다. 컴파일러와
JUnit 은 이미 캐시에 있다. 수첩에 `coretest.sh` 로 적어 뒀다. 요령 둘:

- 시험 코드가 `internal` 을 보려면 **`-Xfriend-paths=<본코드 out>`** 이 필요하다.
  그레이들이 조용히 해 주던 것이다.
- `core/src/main/resources` (언어모델·사전 `.gz`)를 out 폴더에 같이 넣어야 한다.

219개 전부 통과하는 데 1초다. 그레이들보다 빠르다.

## "카톡이랑 별 차이 없는데" — 여기서 8%p 를 더 얻었다

형이 "더 올리는 건 불가능하겠지?" 라고 물어서 어디가 새는지 갈라 봤다. 남아 있던
2.2%p(전체 경로 66.5% vs Kiwi 혼자 68.7%)를 쫓다가 훨씬 큰 것 둘이 나왔다.

### 하나: 불규칙 활용 태그가 통째로 빠져 있었다

`KiwiSpacer.WORD_STARTS` 에 `vv`·`va`·`vx` 는 있는데 **`vvi`·`vai`·`vxi` 가 없었다.**
Kiwi 는 ㅂ·ㅎ·ㅅ 불규칙 용언에 **다른 태그 값**을 준다.

```
백악관은어떻게행동해야할지혼란스럽다
  백악관/NNP  은/JX  어떻/VA-I ← 이게 va 가 아니다
가끔은집안에서당신을돕는사람들이있다
  ...  돕/VV-I ← 이것도 vv 가 아니다
```

그래서 '백악관은어떻게', '당신을돕는' 이 통째로 붙어 나왔다. 불규칙 용언은 드문 말이
아니다 — 돕다·춥다·어렵다·어떻다·그렇다·낫다가 전부 여기다.

넣으니 Kiwi 단계만 재현율 96.8 → **98.3%**, 문장 통째 69.3 → **75.5%**.

### 둘: 짧은 덩어리는 Kiwi 한테 가지도 않았다

`applyLongSplit` 은 **14음절이 넘는 어절만** 넘긴다. 14 는 `MAX_TOKEN_SYLLABLES` —
"디코더가 아예 못 보는 길이" 다. 그걸 "디코더가 잘하는 길이" 로 쓰고 있었다.
길이로 갈라 재 보니 그 착각이 그대로 보인다.

| 공백 전부 지운 3,000 문장 | 14음절 이하 (731) | 넘는 것 (2269) |
|---|---|---|
| 예전 전체 경로 | **51.3%** | 73.4% |
| Kiwi 혼자 | **85.6%** | 72.3% |

**긴 것은 우리가 이미 Kiwi 보다 낫다**(73.4 vs 72.3 — 디코더가 다듬어 주니까).
짧은 것은 디코더 혼자 반도 못 풀고 있었다. 34%p 가 거기 있었다.

문지방을 내리되, **언어모델이 아는 어절은 안 탄다**(흔한 말은 길어도 그대로 둔다).

| 문지방 | 공백 없는 글 통째 | 멀쩡한 글을 건드림 |
|---|---|---|
| 14 (예전) | 68.0% | 0.80% |
| **8 (채택)** | **75.8%** | **0.97%** |
| 6 | 76.4% | 1.83% |
| 5 | 76.5% | 3.47% |

8 에서 멈춘 이유: 6 은 0.6%p 더 얻자고 오교정을 0.9%p 더 내는데, 그 오교정이
'중국요리사들 → 중국 요리사들', '스파르타인들 → 스파르타 인들', '물어봐야겠어요 →
물어 봐야겠어요' 처럼 멀쩡한 말을 가르는 것이다.

같이 넣은 것: **여는 괄호 뒤에는 안 띄운다.** Kiwi 가 '이루어졌다(유나이티드' 를
'이루어졌다( 유나이티드' 로 만들고 있었다.

`AnalyzeOption` 에 오타 변형기를 넘기면 분석기가 "이 글자를 저 글자로 바꾸면 말이

### 처음엔 못 쓸 물건이었다

`Kiwi.join()` 으로 문장을 통째로 다시 만들어 봤더니 **멀쩡한 글의 29.9%를 건드렸다.**
join 은 띄어쓰기까지 자기 규칙으로 다시 매긴다 — '되어 → 돼', '체크포인트 → 체크 포인트',
'할려고 했어 → 할려고했어'. 이걸 그대로 쓰면 재앙이다.

### 쓸 수 있게 만든 세 가지

1. **어절 단위로 좁힌다.** 문맥은 문장 전체로 보되, 되짚어 다시 만드는 것은
   `typoCost` 가 붙은 어절 하나다. 나머지 글자는 원문 그대로 둔다.
2. **공백이 끼어들면 버린다.** 이 단계는 맞춤법만 맡는다. 띄어쓰기는 Kiwi 띄어쓰기와
   디코더가 이미 하고 있고, 둘이 같은 자리를 두고 다투면 안 된다.
3. **말뭉치가 아는 낱말은 안 건드린다.** 이게 제일 크다.

'줄리안 → 줄리아' 처럼 **멀쩡한 낱말을 다른 멀쩡한 낱말로** 바꾸는 것들이다.

`th=1.5` (Kiwi 기본값 2.5) — 낮춰도 되살림은 같고 이미 틀어진 글을 엉뚱하게 바꾸는
비율만 내려간다. `basicTypoSet` 만 쓴다 — `WithContinual` 은 오교정만 늘렸다.

## 받침을 빠뜨린 오타를 못 고치고 있었다 (0.4 → 50.6%)

편집 표(`JONGSEONG_EDITS`)를 보니 **받침 혼동**만 있고(ㅅ↔ㅆ, ㄷ→ㅅ, 겹받침 한쪽) 받침을
**통째로 넣는** 편집이 없었다. 다른 편집은 "자모를 잘못 친 것" 인데 받침 누락은
"키를 하나 덜 친 것" 이라 종류가 다르다. 두벌식에서 받침은 한 번 더 눌러야 해서 흔하다.

ㄱㄴㄹㅁㅂㅅㅇ 을 넣는 편집을 3.0 값으로 더했다.

| | 받침 되살림 | 멀쩡한 글 건드림 |
|---|---|---|
| 없음 | 0.4% | 1.00% |
| 값 2.5, 문지방 없음 | 62.7% | 1.20% |
| 값 3.0, 문지방 없음 | 60.2% | 1.17% |
| **값 3.0, 드문 말만(ln<3)** | **50.6%** | **1.07%** |

### 문지방이 필요한 이유

문지방 없이 열어 두면 **뜻이 바뀐다.** 늘어난 오교정 다섯을 들여다봤더니:

```
서명해 주셨으면  →  설명해 주셨으면
심장 세포는 이식될  →  심장 세포는 인식될
어떻게 끝내는지  →  어떻게 끝냈는지
```

전부 멀쩡한 낱말을 다른 멀쩡한 낱말로 바꾼 것이다. 받침이 빠지면 거의 언제나
**없는 말**이 되므로, 흔한 말에까지 이 편집을 열어 줄 이유가 없다. ln(빈도) 3
(6,700만 어절에 스무 번)보다 드문 어절에만 허용한다.

"아예 모르는 말만"(문지방 0)도 대 봤는데 되살림이 45.5% 로 5%p 낮으면서 오교정은
똑같았다. 3 이 낫다.

받침을 **빼는** 편집도 대 봤다. 전 항목이 나빠진다(오교정 1.53%). 안 넣는다.

속도는 되레 빨라졌다(창 하나 0.074 → 0.047ms) — 드문 말에만 도니까.

2. **디코더에 Kiwi 쪼갬을 후보로 주기**(`pieceSplitter`) — 띄어쓰기 복원 73.7 → 73.8%.
   변화 없음. 결합만 늘어서 버렸다. 디코더의 자유 구간이 이미 그 자리를 보고 있다.
3. **문지방 내리기 재시험** — Kiwi 가 좋아졌으니 다시 재 봤는데 결론이 같다.
   6 → 오교정 1.67%, 5 → 2.97%, 4 → 4.90%. 8 이 맞다.
4. **디코더 값 흔들기**(`SPLIT_COST`, `NOUN_JUNCTION_COST`) — 어느 쪽으로 움직여도
   띄어쓰기 0.5%p 를 오교정 0.1~0.2%p 와 바꾸는 거래다. 지금 값이 최적선 위에 있다.

## 실기기에서 터질 수 있던 것 둘 (고침)

1. **Kiwi 를 올리는 동안 키보드를 닫으면** 모델 100MB 가 샌다. `onDestroy` 가 먼저
   끝나고 그 뒤에 올라온 것을 아무도 닫지 않는다. `destroyed` 깃발로 막았다.
2. **전체교정 도중에 키보드를 닫으면** 네이티브 객체를 닫고 그 위에서 계속 읽는다 —
   자바 예외가 아니라 **프로세스가 통째로 죽는 종류**다. `space`/`fix`/`close` 를 같은
   자물쇠로 묶고 `closed` 깃발로 한 번 더 막았다.


## 컴파일 오류를 세 번 연속 CI 에 올렸다

`KiwiSpacer.open` 의 반환형이 `KiwiSpacer?` 인데 `.onSuccess { opened -> opened.close() }`
로 썼다. 코틀린은 nullable 수신자에 점을 못 찍는다. 빌드 #92·#93·#94 가 같은 이유로
죽었는데 **올리고 다음 일로 넘어가느라 세 번을 못 봤다.**

두 가지가 겹쳤다.

1. **지역 검사가 반쪽이었다.** `KiwiSpacer.kt` 만 껍데기로 감싸 컴파일하고 있었고,
   같이 고친 `SpellKeyboardService.kt` 는 안 봤다. 바로 그 파일에서 났다.
2. **올린 뒤 결과를 안 봤다.** 이게 더 큰 잘못이다.

### 고친 것

- `tools/localcheck/typecheck-keyboard.sh` — **키보드 모듈 전체**를 타입 검사한다.
  일부러 그 버그를 다시 넣어 보고 잡는 것을 확인했다(통과만 하는 검사는 검사가 아니다).
- 규칙: **올린 뒤에는 빌드 결과를 확인하고 나서 다음 일로 넘어간다.**

### 왜 안드로이드 SDK 없이 되는가

`dl.google.com` 이 막혀서 안드로이드 SDK 도 androidx 도 못 받는다. 대신

- `android.jar` → **메이븐 중앙**의 `org.robolectric:android-all`(구글 메이븐이 아니다)
- androidx·결제·ML Kit → `tools/localcheck/stubs/` 에 **쓰는 자리의 서명만** 흉내낸 껍데기
- `R`·`BuildConfig` → 소스에서 이름을 긁어 매번 다시 만든다
- Kiwi → `build.gradle.kts` 의 판 번호를 읽어 AAR 을 받아 `classes.jar` 만 꺼내 쓴다

껍데기는 **돌리기 위한 것이 아니라 타입을 맞추기 위한 것**이다. 새 API 를 쓰기 시작하면
"unresolved reference" 가 나고, 그 자리의 서명만 `stubs/` 에 더하면 된다.

**못 잡는 것**: 리소스·매니페스트·프로가드·실제 실행. 그건 CI 몫이다.

## 오타 교정기를 파이프라인 **맨 뒤**로 옮겼다

처음엔 맨 앞에 뒀다. "분석기가 먼저 꼴을 되돌려 놓으면 그 뒤 규칙이 걸릴 것이 늘어난다"
고 생각했는데 **거꾸로였다.**

말뭉치 숫자만 보고 있었으면 못 찾았다. 실기기에서 쓸 법한 문장 서른 줄을 **앱에 들어가는
코드 그대로** 돌려 보니 두 줄이 되레 나빠져 있었다.

```
내가 그랬다고 햇어   →  내가 그랬다고 해서    (규칙은 '햇 → 했' 을 안다)
내일 다시 연라할게   →  내일 다시 열라할게    (디코더는 '연락할게' 를 안다)
```

**정확히 아는 것(규칙 표)과 근거를 견주는 것(디코더)이 있는데, 넘겨짚는 쪽을 먼저
돌리면 그 답을 뒤집을 수가 없다.** 맨 뒤로 옮기니 둘 다 제 답을 찾고, 말뭉치 숫자도
전부 좋아졌다.

| | 앞 | **뒤** |
|---|---|---|
| ㅐ/ㅔ 되살림 | 88.0% (엉뚱 2.2%) | **88.3%** (엉뚱 **2.0%**) |
| 받침 되살림 | 50.5% (엉뚱 6.3%) | **51.4%** (엉뚱 **5.4%**) |
| 옆 키 되살림 | 39.0% (엉뚱 9.9%) | **42.7%** (엉뚱 **6.2%**) |
| 띄어쓰기 하나 | 73.7% | 73.8% |
| 멀쩡한 글 건드림 | 1.20% | 1.20% |

**교훈: 말뭉치 숫자만 보지 말고 실제 문장을 눈으로 봐라.** 오교정 1.20% 는 두 순서가
똑같았다. 숫자가 같다고 같은 것이 아니다.

## 타이핑 중 교정은 전체교정보다 6~10%p 낮다 (구조적)

한 번도 안 재 봤던 것이라 재 봤다. 어절을 치고 스페이스를 누를 때마다 커서 앞 세
어절만 다시 보는, 실제 그 길을 그대로 흉내냈다(`scratchpad/kiwi/Live.java`).

| | 타이핑 중 | 전체교정 |
|---|---|---|
| ㅐ/ㅔ 되살림 | 77.9% | 88.3% |
| 받침 되살림 | 44.3% | 51.4% |
| 옆 키 되살림 | 30.0% | 42.7% |
| 멀쩡한 글 건드림 | 0.85% | 1.20% |

창을 3 → 5 어절로 넓혀도 **소수점까지 똑같다.** 창 크기 문제가 아니다. 타이핑 중에는
**뒷문맥이 없다** — 마지막 어절은 다음 어절을 칠 때에야 양쪽 문맥을 갖는다. 문장의
마지막 어절은 영영 못 갖는다. 이건 값으로 메울 수 있는 것이 아니다.

그래서 '전체' 단추가 있는 것이고, 그 차이가 이 표만큼이다.

## AI 모델은 느낌이 아니라 숫자로 고른다 → `server/bench/`

온디바이스는 처음부터 숫자로 골라 왔는데 **AI 만 느낌으로 고르고 있었다.** 그러다
"원래 제미나이보다 떨어진다" 는 말 한마디에 모델 이력을 뒤져 `gemini-3.8-flash` 로
올렸다가 바로 되돌렸다 — 요청받지도 않았고 단가도 모르는 채였다.

이제 겨루기 판이 있다. `bench/` 를 건드리면 CI 가 돈다(기본 가지가 다른 프로젝트 것이라
손으로는 못 돌린다).

```
server/bench/sentences.json   폰에서 칠 법한 한국어 50문장. 직접 썼다 — 남의 말뭉치를 안 넣으려고
server/bench/inject.mjs       오타 심기. 온디바이스를 잴 때와 같은 다섯 갈래, 씨 고정
server/bench/models.mjs       같은 지시문으로 여러 모델에 보내고 점수를 낸다
server/bench/pre-spaced.json  폰 안 엔진이 붙여 쓴 글을 푼 결과 (scratchpad/kiwi/PreSpace.java 가 만든다)
```

**되살림만 보고 고르지 마라.** 멀쩡한 글 건드림을 같이 봐야 한다 — 안 그러면 아무거나
막 고치는 모델이 1등 한다.

## 띄어쓰기는 우리가, 맞춤법은 AI가

겨루기에서 제일 크게 갈린 항목이 이거다. 띄어쓰기를 통째로 지운 글에서

```
우리 (폰 안, 공짜, 0.07ms)   문장 통째 78.1%  (겨루기 50문장으로는 86.0%)
gemini-3.5-flash-lite        문장 통째 70.0%, 게다가 30% 를 엉뚱하게 바꾼다
```

**우리가 더 잘하는 일을 돈 주고 시키면서 결과까지 나빠지고 있었다.** 맞춤법은 저쪽이
훨씬 낫다(92~96%). 각자 잘하는 것만 시킨다 — `SpellKeyboardService.spacedForServer` 가
보내기 전에 붙여 쓴 덩어리만 먼저 푼다.

**풀 것이 있을 때만 판다.** 먼저 푸는 데도 시간이 들어서(2,000자면 폰에서 몇 초)
`CorrectionEngine.hasGluedRun` 으로 훑어보고 없으면 아무 일도 안 한다.

## 전체교정은 몇 자까지 되나 (2026-09-14)

코드상 한도는 4만 자(`FULL_BEFORE_CHARS` + `FULL_AFTER_CHARS`). 36음절씩 잘라 순서대로
처리하므로 길이 자체는 문제가 안 된다. **한계는 시간이다.**

| 글자 수 | 데스크톱 | 폰 환산(×20) |
|---|---|---|
| 100자 | 14ms | 0.3초 |
| 500자 | 52ms | 1.0초 |
| 1,000자 | 72ms | 1.4초 |
| 2,000자 | 332ms | 6.6초 |
| 10,000자 | 1.2초 | 23초 |
| 40,000자 | 4.7초 | 94초 |

**실용 한계는 2,000자 근처다.** 실시간 교정은 이것과 무관하다(창이 세 어절이라 글 길이와
상관없이 0.07ms).

**잴 때 주의**: 같은 문장을 반복해 붙이면 어절 캐시가 다 맞아서 40,000자가 20,000자보다
빠르게 나온다. 서로 다른 문장으로 재야 한다. 엔진을 새로 만들면 그 시간이 섞이므로
(100자에 163ms) 실제 앱처럼 데워 놓고 재야 한다.

## 겨루기가 구글 크레딧을 바닥냈다 (2026-09-15)

실기기의 AI 교정이 멈췄다. 서버는 멀쩡했고 구글이 429 로 막았다 —
`Your prepayment credits are depleted.` **재는 도구가 파는 물건을 세웠다.**

### 뭘 잘못했나

1. **자동 방아쇠.** `server/bench/**` 를 건드리면 돌게 해 뒀다. 기본 가지가 다른
   프로젝트 것이라 손으로 못 돌려서 낸 꾀였는데, 시험지를 손볼 때마다 모델 셋에
   347문항씩 나갔다. 네 판이 돌았다.
2. **숙고를 안 껐다.** 앱은 `thinkingBudget: 0` 으로 보내는데 겨루기는 안 보냈다.
   숙고 토큰은 **출력 요금**으로 청구된다. `gemini-3.8-flash` 한 판이 598초 걸린 것이
   그 표시였는데 그걸 "느리네" 로만 읽었다.
3. **값을 모르는 모델을 돌렸다.** `gemini-3.5-flash`·`gemini-3.8-flash` 의 단가를
   확인한 적이 없다. 수첩의 조사표에 없는 모델이었다.
4. **돌기 전에도 돌고 나서도 값을 안 찍었다.** 그래서 바닥날 때까지 몰랐다.

### 막아 둔 것

- **자동 방아쇠를 뽑았다.** `workflow_dispatch` 뿐이고, 기본 가지에 올라가야 손으로
  돌릴 수 있다. 그때까지는 아예 안 돈다. 값이 드는 일은 사람이 누를 때만 돌아야 한다.
- 돌릴 때 `돈 쓴다` 를 정확히 쳐야 한다. 안 치면 멈춘다.
- 문장 수 기본값이 10이다(약 70문항). 전부 돌리려면 일부러 50을 적어야 한다.
- **돌기 전에 예상 값**을 모델별로 찍는다. 값을 모르는 모델은 "값을 모르는 모델이다"
  라고 찍고 넘어간다 — 지어내면 "얼마 안 나가겠지" 하고 돌리게 된다.
- **끝나고 실제로 쓴 토큰과 값**을 찍는다. 추정이 아니라 응답이 알려 준 사실이다.
- 겨루기도 앱과 같이 `thinkingBudget: 0` 으로 보낸다. 앱이 받는 것과 다른 것을 재고
  있으면 그 숫자는 애초에 쓸모가 없다.

### 규칙

**남의 돈이 나가는 일은 기본값이 "안 함" 이어야 한다.** 편하려고 자동으로 돌게 두지
마라. 여기서는 그 편의가 실기기의 기능을 세웠다.

## OpenAI 쪽은 숙고를 끄면 못 쓴다 (2026-09-15, 재서 확인)

구글 크레딧이 바닥나 `gpt-5-nano` 로 옮겼는데 실기기에서 "교정이 오래 걸린다" 가 나왔다.
`/stats` 의 실사용 숫자가 원인을 바로 보여줬다.

```
9/15  요청 8회  입력 5,727  교정문 596  숙고 3,968
      → 한 번에 숙고 496토큰, 교정문(74토큰)의 6.7배
```

숙고 토큰은 **출력 요금**으로 청구된다. 이것 때문에 값이 4배고, 그 시간이 그대로
대기 시간이다. 6배 싼 모델로 옮겼는데 이득이 통째로 날아가 있었다(2,000원어치가
제미나이 34.5만 자, nano+숙고 34만 자로 똑같았다).

**그래서 숙고를 끄고 재 봤더니 품질이 무너진다.**

| (숙고 끔) | nano 35문항 | mini 28문항 | 참고: 제미나이 3.5-flash-lite |
|---|---|---|---|
| 전부→우리가먼저 | 60.0% | 75.0% | **92.0%** |
| **멀쩡한 글 건드림** | **20.0%** | **33.3%** | **2~4%** |

mini 가 nano 보다 나을 거라 봤는데 **멀쩡한 글 건드림은 오히려 더 나빴다**(33.3%).
크기 문제가 아니라 **숙고가 하던 일이 있었다**는 뜻이다. 문항 수가 적어 소수점은
못 믿지만, 제미나이의 2~4% 대 20~33% 는 그 정도 표본으로도 갈리는 차이다.

### 결론

- OpenAI 로 갈 거면 **숙고를 켜야 한다.** 그러면 느리고, 값 이득도 없다.
- **제미나이 3.5-flash-lite 가 여전히 제일 낫다** — 1.1초, 92~95%, 건드림 2~4%.
  구글 크레딧만 채우면 된다.

### 먼저 시험지를 만들었다

기존 시험지(`spacing/keep.txt`·`split.txt`, 50문장)는 **회귀 그물**이지 자가 아니다.
얼마나 좋은지를 재려면 다른 것이 필요했다.

  격식체(KorNLI)만 보고 있으면 진짜 약한 자리가 안 보인다. 실제로 기준선에서
  구어체 복원은 59.5%, 격식체는 72.0% 로 **13%p 나 벌어져 있었다.**

- `tools/localcheck/explain.sh` — 디코더가 왜 그렇게 골랐는지 점수를 풀어 본다.
  **이번 작업의 절반은 이 도구가 했다.**

시험지를 만들 때 한 번 헤맸다: 처음에는 보조용언을 **원칙대로 띄어 쓴 꼴**을 정답으로
뒀는데, 붙여 쓰는 것도 맞아서(제47항) "둘 다 맞는 것" 을 틀렸다고 세고 있었다.
사람들이 실제로 치는 붙여 쓴 꼴로 정답을 바꿨다.

격식체 오교정이 여덟에서 열여섯으로 늘었는데, **여덟 중 여섯은 틀린 것이 아니다** —
'연습 문제'·'특별 활동'·'치과 대학'·'공동 작업'·'상업 지역'. 전문 용어는 제50항이
단어별로 띄어 씀을 원칙으로 한다. 진짜 새 오교정은 둘('취급하는 지에', '지지 해본').

### 고친 것 1 — 규칙 (`SpacingRules`)

관형사형 뒤 의존명사(거·게·건지·데·지·만큼·뿐·바·채·척·체·리·뻔·만하·중·듯·대로),
수관형사·단위(스물~아흔, 십·백·천, 시·분·초·원·달·곳·줄·벌·끼), 부정의 못·안,
부사 좀, 보조용언 '-고 싶다'·'-지 마'.

통계로는 안 되는 자리다. 말뭉치에 '할거야'가 붙어 있어서 언어모델이 한 낱말로 알고,
그러면 디코더가 거기서 멈춘다.

**값싼 규칙이 낼 수 있는 가장 나쁜 실수를 하나씩 막았다.** 겪은 것만 적는다.

| 넣었더니 | 막은 법 |
|---|---|
| `주십시오` → `주십 시오` | 수관형사를 어절 첫머리에서만 본다 |
| `이해하지 못했다` → `못 했다` | '하다'의 활용형을 통째로 뺀다 (0.8% → **2.8%** 였다) |
| `격주로 열리는` → `열 리는` | 의존명사 '리'는 '-리는'을 안 받는다 |
| `무한대로`·`절대로` | '대로'는 좁은 판정(는·은·ㄹ) |
| `노력했는데도` → `했는 데도` | '데'는 **조사를 받을 때만** ('데가'·'데를') |
| `돈만큼`·`사람뿐` | 조사로도 쓰이는 의존명사는 좁은 판정 |

예전 예외표에 '한개'·'세번'·'두장'처럼 **낱말이 아닌 것**이 들어 있어서, 정작 띄어야 할
'사과 세 개'를 규칙이 막고 있었다. 진짜 낱말만 남겼다.

### 고친 것 2 — 디코더 (`ContextCorrector.rejoinOptional`)

**여기가 제일 컸다.** 사전은 이미 제대로 나누고 있었고, `rejoinOptional` 이 도로
붙이고 있었다.

    비가왔어      사전나눔 = 비가 왔어      → 도로 붙임
    받아서미안    사전나눔 = 받아서 미안    → 도로 붙임
    먹었어고마워  사전나눔 = 먹었어 고마워  → 도로 붙임
    오늘날씨가    사전나눔 = 오늘 날씨가    → 도로 붙임
    잘해결됐어    사전나눔 = 잘 해결됐어    → 도로 붙임

도로 붙이면 **"사전이 나눴다" 는 사실 자체가 사라진다.** 그러면 `unknownScore` 가
그 덩어리를 "무리 없이 분석되는 드문 낱말"(−22)로 보고, `boundaryCost` 는 나눈
가설에 12점짜리 벽까지 세운다. 정답이 후보에 오르지도 못한다.

세 가지가 잘못 판정하고 있었다.

1. **보조적 연결어미 '-아/-어' 판정이 마지막 음절 모양뿐이었다** (받침 없이 ㅏ·ㅓ 계열).
   '비가'(체언+조사), '받아서'(연결어미), '먹었어'(종결어미)가 죄다 걸렸다.
   → 어미로 끝날 것 + '-아서/-어서'가 아닐 것 + 앞 음절 받침이 ㅆ 이 아닐 것.
2. **명사|명사를 연쇄 빈도로만 판단했다.** 말뭉치가 6천만 어절뿐이라 멀쩡한 짝도
   대부분 안 나온다 — '오늘 날씨가' 조차 없다. → 연쇄를 못 봤으면 **두 조각이 저마다
   흔한 낱말인지**를 본다(`NOUN_SPLIT_MIN_PIECE_LN`, ln 6).
3. **한 음절 조각을 사전 말만 듣고 조사·어미로 봤다.** 사전은 '잘'·'더'·'다'·'안'을
   어미로도 읽는다. → 어절로 얼마나 나왔는지를 같이 본다(`SINGLE_WORD_MIN_LN`, ln 11).
   가르는 선이 여기 있다: 부사 11.1~12.1 vs 조사 8.4~9.4.

### 한계선을 어디서 봤나

문지방을 더 내리면 계속 오르지만 **진짜 오교정이 나오는 지점**이 있다.

| `NOUN_SPLIT_MIN_PIECE_LN` | 구어체 복원 | 격식체 오교정 | 새로 깨지는 것 |
|---|---|---|---|
| 없음 | 75.2% | 0.83% | |
| 7 | 77.5% | 1.17% | (특별 활동 — 맞는 표기) |
| **6** | **77.9%** | **1.60%** | (연습 문제·치과 대학 — 맞는 표기) |
| 5 | 78.8% | 2.00% | 교육 **과학기술 부가** ← 여기서부터 틀린다 |
| 4 | 79.7% | 2.67% | 무도회 **장의** |

6 에서 멈췄다. 5 부터는 기관 이름이 엉뚱한 자리에서 끊긴다.

### 마지막에 잰 몇 가지 (다 버렸다)

숫자가 안 움직이거나 나빠져서 안 넣은 것들. **다시 해 보지 말라고 적어 둔다.**

| 해 본 것 | 결과 |
|---|---|
| `WELL_FORMED_FIRM_COST` 를 0 → −1500·−3000 | 잡음. 오교정만 하나 늘었다 |
| "본 적 있다" 를 빈도에 비례하는 값으로 | **아무 변화 없음.** 이 벽은 여기서 병목이 아니다 |
| `MARGIN` 1.5 → 1.2·1.0 | 순손해. 오교정이 늘고 복원은 그대로 |
| `EC`·`EF` 를 어절 경계 표시에 추가 | 0.1%p. 남겨는 뒀지만 기대한 만큼은 아니었다 |

### 남은 숙제

`keep.txt` 에서 **끊는 자리 자체가 틀리는** 것 셋. 나누기를 넓히거나 좁히는 것으로는
안 고쳐진다 — 형태소 사전이 긴 덩어리를 나눌 때 나는 오류다.

    근로기준법시행령이 → 근로 기준 법시 행령이   ('법시'·'행령'은 낱말이 아니다)
    부동산실거래가신고를 → 부동산 실 거래가 신고를
    사회복지사자격증을 → 사회 복지 사 자격증을   ('사'가 떨어져 나왔다)

그리고 **글자가 이미 붙어 버린 수량**('책두 권', '아메리카노한 잔')은 수관형사 규칙이
어절 첫머리만 보기 때문에 못 닿는다. 디코더가 먼저 '책|두'를 갈라야 규칙에 걸린다.

### 잴 때

    curl -fsSL -O https://raw.githubusercontent.com/kakaobrain/kor-nlu-datasets/master/KorNLI/xnli.dev.ko.tsv
    curl -fsSL -O https://raw.githubusercontent.com/kakaobrain/kor-nlu-datasets/master/KorNLI/xnli.test.ko.tsv
    SPELL_EVAL_FILES=xnli.dev.ko.tsv,xnli.test.ko.tsv tools/localcheck/eval-spacing.sh

**네 숫자를 같이 봐라.** 하나만 보고 올리면 나머지가 조용히 나빠진다. 그리고 오교정
목록은 **눈으로 읽어라** — 둘 다 맞는 표기를 틀렸다고 세고 있을 수 있다.

## 한도 1만 자 · 결제 화면 정리 (2026-09-20)

### 한도를 2만 → 1만으로

기준을 하나로 정했다: **어떻게 쓰든 구독 하나가 적자를 못 내야 한다.** 한 번 값은
지시문 고정분 0.12원 + 글자당 0.0046원이라 짧게 여러 번 보낼수록 비싸고, 그래서 같은
한도라도 어떻게 채우느냐에 따라 값이 다르다.

| 매일 꽉 채우는 방식 | 1만 자 | 2만 자 |
|---|---|---|
| 50자씩 (최악) | 2,100원 | 4,200원 |
| 200자씩 | 1,560원 | 3,120원 |
| 2,000자씩 | 1,398원 | 2,832원 |

받는 돈은 2,990원(실수령 2,691원). 2만은 덩어리 크기와 상관없이 꽉 채우면 적자였다
(글자당 값만으로 하루 92원 > 89.7원). 1만은 최악에도 남는다. 보통 사용자(하루 5천 자,
월 780원)는 어느 쪽이든 못 느낀다.

바꾼 자리 셋이 같이 가야 한다: `server/wrangler.toml` 의 `SUB_DAILY_CHARS`(실제 한도),
`PaywallActivity.DAILY_CHARS`(횟수 안내), `GeminiCorrector` 의 한도 문구.

### 결제 화면

무료|프리미엄 알약을 뺐다. 눌러도 아래 버튼 글자만 바뀌는, 고르는 척하는 부품이었다.
제목은 "프리미엄" 하나를 크게, 아래는 비교표뿐이다. 칸은 **✓ 아니면 ✗** — 둘 다 되는
것은 양쪽 ✓, 무료에 없는 것은 무료 쪽 빨간 ✗. 글자로 된 칸("기본 번역"/"AI 번역")은
뺐다. 횟수 줄(100자·500자·2,000자 기준)만 숫자고, 그것도 무료 쪽은 ✗ 다.

무료는 AI 를 아예 못 쓴다. 그건 그대로다.

## 무료 사용자가 서버를 두드리던 것을 끊었다 (2026-09-22)

DAU 10 만을 가정하고 서버 부담을 세어 보다가 찾았다.

못 쓰는 무료 사용자도 키보드 프로세스가 새로 뜰 때마다 서버를 한 번씩 쳤다.

모델로 갈지는 서버가 정한다). 앱이 구글을 직접 부르던 시절의 잔재다.

끊었다. 남은 것은 하루 2 만이고, 그건 전부 구독자가 실제로 쓴 것이다.

**모델 갈아타기는 그대로 산다.** 교정하다 거절당하면 `GeminiCorrector` 가 그때 목록을
받아 옮긴다(`candidates()`). 그 한 왕복은 실제로 옮겨야 할 때만 든다.
`prefetchModels()` 는 코어에 남겨 뒀다 — 시험이 여섯 개 붙어 있고, 나중에 앱이 구글을
직접 부르는 길이 생기면 그때 쓸 자리다. 지금은 아무도 안 부른다.

## 로그인 — 구독을 폰 밖으로 (2026-09-22)

윈도우 프로그램에서 구독을 같이 쓰려다 막혔다. 구독은 **Play 구매 토큰** 하나로 도는데
윈도우에는 스토어가 없고 아이폰은 다른 스토어다. 물어볼 데가 없으니 계정이 필요했다.

설계와 서버 쪽은 **`docs/ACCOUNTS.md`** 에 적었다. 여기서는 요점만.

    계정 ──가리킴──> 구매 토큰 ──확인──> Google Play

**계정은 포인터일 뿐이다.** 구독 상태의 진실은 여전히 Play 라, 환불·해지·만료를 우리가
따로 관리하지 않는다. 하루 한도도 그대로 산다 — 기기 토큰이 계정을 거쳐 같은 구매로
풀리므로 "결제 하나에 한도 하나" 가 저절로 지켜진다.

### 안드로이드 쪽에서 한 일

- `AccountManager` — Credential Manager 로 구글 계정 창을 띄워 **ID 토큰**을 받고,
  `/v1/account/signin` 에 구매 토큰과 함께 보낸다. 돌려받은 기기 토큰은 `Prefs` 에.
- `Prefs.serverHeaders` 가 `X-Device-Token` 을 같이 싣는다. 서버는 **구매 토큰 쪽을 먼저**
  믿는다 — Play 에 직접 물어볼 수 있는 쪽이다.
- 첫 화면 위 막대에 로그인 버튼. **폰만 쓰는 사람에게는 소용이 없다**(Play 가 알아서
  복원한다). 그래서 설명도 "윈도우·아이폰에서도 같은 구독을 쓰려면" 이라고 적었다.

### 빌드할 때 넣어야 하는 것

| 어디 | 이름 | 없으면 |
|---|---|---|
| 앱 | `GOOGLE_CLIENT_ID` (`build-apk.yml` 에 적힘) | 로그인 버튼이 **통째로 숨는다** |
| 서버 | `GOOGLE_CLIENT_IDS` | 로그인이 503 으로 막힌다 |

**둘이 짝이 맞아야 한다.** 서버는 토큰의 `aud` 가 그 목록에 있는지 본다 — 이 검사가
없으면 남의 앱에 발급된 멀쩡한 구글 토큰으로도 우리 계정에 들어온다. 안드로이드가
`aud` 에 넣는 것은 **웹 클라이언트 ID** 다(안드로이드 클라이언트 ID 가 아니다).
2026-09-23 에 사용자 계정 "스펠 키보드" 프로젝트에 웹·Android 클라이언트를 만들어 양쪽에
넣었다. 콘솔 쪽 사정(테스트 사용자, Play 올릴 때 SHA-1 하나 더)은 `docs/ACCOUNTS.md`.

### 남은 것

**계정 삭제.** 계정을 만드는 앱은 앱 안 삭제 + 웹에서 요청할 주소를 둬야 한다(Play 정책).
출시 전에 필요하다.

## 첫 화면과 환경설정을 나눴다 (2026-09-23)

한 화면에 로그인까지 들어가니 너무 길어져서 정작 할 일(키보드 켜기, 써 보기)이 묻혔다.

| 화면 | 담은 것 |
|---|---|
| 첫 화면 `SetupActivity` | 위 막대(앱 이름 · **로그인** · **환경설정**), 시작하기, 써 보기, 사용법, 프리미엄 |
| 환경설정 `SettingsActivity` | 실시간 교정 스위치, 자판·테마·배경·투명도, 정보(개인정보·AI 안내, 설치 ID) |

- **자판 도구 줄의 설정 버튼은 환경설정으로 간다.** 자판·테마를 바꾸러 누르는 버튼이라서다.
  사용법 그림의 설명도 그에 맞춰 고쳤다.
- 로그인 버튼: 로그인 전엔 "로그인"(누르면 바로 계정 창), 뒤엔 "내 계정"(누르면 상태 + 로그아웃).
- 테마를 바꾸면 환경설정이 다시 만들어지고, 돌아가면 첫 화면도 다시 만들어진다. 둘 다
  스크롤 위치를 살린다. 밝기 값은 `ThemeMode.nightMode()` 하나를 같이 쓴다.
- 위 막대는 360dp 폰에서 제목과 버튼 둘이 한 줄에 들어가게 제목 22sp 로 맞췄다.

## ☰ 더보기로 모았다 — 로그인 프로필, 회원 탈퇴, 약관 (2026-09-24)

위 막대에 [로그인] [환경설정] 을 늘어놓았더니 "지저분하고 따로 논다" 는 평. ☰ 하나로 모았다.

| 화면 | 담은 것 |
|---|---|
| 첫 화면 `SetupActivity` | 앱 이름 + ☰ / 시작하기, 써 보기, 사용법, 프리미엄(+ AI 안내 한 줄) |
| 더보기 서랍 `MoreDrawer` | 계정 칸 / 키보드 맞춤설정 · 개인정보 처리방침 · 서비스 이용약관 · 고객센터 / 버전·설치 ID |
| 키보드 맞춤설정 `SettingsActivity` | 실시간 교정, 자판·테마·배경·투명도, 개인정보 안내 한 줄 |

- **계정 칸**: 로그인 뒤 구글 프로필 사진(동그랗게) + 이름, 밑에 로그아웃 · 회원 탈퇴.
  사진이 없으면 이름 첫 글자. 이름·사진은 **폰에만** 둔다(`Prefs.profileName`, `ProfilePhoto`) —
  서버는 여전히 `sub` 해시만 안다. 이미지 라이브러리 없이 `HttpURLConnection` + `BitmapShader`.
- **회원 탈퇴**: 서버 `/v1/account/delete` 새로. 자세한 것은 `docs/ACCOUNTS.md`.
- **약관 두 개는 서버 페이지**(`/privacy`, `/terms`)를 브라우저로 연다. Play Console 에 적는
  주소와 같은 곳이라 두 벌이 생기지 않는다. `/privacy` 는 예전 글(무료 횟수·IP 한도 이야기)이
  남아 있어서 지금 사실대로 새로 썼다 — 계정, 국외 이전(Cloudflare·Google), 탈퇴(#delete).
- **고객센터**: 메일 앱을 열고 본문 밑에 버전·기기·설치 ID 를 붙인다.

### 채워야 할 빈칸

| 어디 | 무엇 | 비어 있으면 |
|---|---|---|
| 앱 `strings.xml` `support_email` | 고객센터 메일 | "준비 중이에요" 가 뜬다 |
| 서버 `CONTACT_EMAIL` | 방침·약관의 문의처 | 그 줄이 안 나온다 |
| 서버 `OPERATOR_NAME` | 방침·약관의 운영자 | 그 줄이 안 나온다 |

Play Console 에 적을 주소: 방침 `…workers.dev/privacy`, 계정 삭제 `…workers.dev/privacy#delete`.

### 따로 화면 → 서랍 (같은 날)

더보기가 "아예 다른 창으로 넘어간다" 는 평. **오른쪽에서 밀려 나와 화면 폭의 반을 덮고, 나머지
반은 어둡게 깔리는 서랍**으로 바꿨다(`MoreDrawer` + `more_drawer.xml`, 첫 화면에 `<include>`).
어두운 곳 · ✕ · 뒤로 가기로 닫힌다. `DrawerLayout` 은 안 들였다 — 막 하나와 판 하나를 애니메이션
하는 것으로 충분하다.

- 폭은 화면의 반(360dp 폰에서 180dp). 좁아서 카드 대신 구분선, 로그아웃·회원 탈퇴는 위아래로,
  메뉴 글씨 15sp. 가로 화면·태블릿에서는 400dp 에서 멈춘다.
- 서랍에서 키보드 맞춤설정 → 테마 변경 → 돌아오면 첫 화면이 다시 만들어진다. 서랍을 연 채로
  애니메이션 없이 되살린다(`KEY_MORE_OPEN`).
- 열 때 써 보기 칸의 자판을 내린다 — 안 그러면 자판이 서랍을 가린다.

**폭은 3분의 2 로 넓혔다(같은 날).** 반(180dp)은 실기기에서 좁다는 평. `MoreDrawer.open()` 의
`widthPixels * 2 / 3` 한 곳만 바꾸면 된다. 360dp 폰에서 240dp, 400dp 에서 멈추는 것은 그대로.
